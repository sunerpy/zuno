WHY THIS PROVES EXIT-ORDER EVICTION, NOT CREATION-ORDER
  Evicted = {25, 26, 27, 28, 29} = the five EARLIEST exits, which are the five
  NEWEST creations. Creation-ordered eviction would have produced {0, 1, 2, 3, 4}.
  The two sets are disjoint, so the test cannot pass under the wrong rule. The
  last line names the five survivors a creation-ordered port would have thrown
  away, and all five are retained.

  The retained queue is asserted with `assert_eq!` against the exact 25-element
  exit-order slice, not with a length check:
      assert_eq!(service.retained_exited(), expected_retained, ...)

RETAINED-BUT-EXITED SESSIONS STAY OBSERVABLE (pty.ts:15-16)
  Every retained session still answers for status, exit code and output:

      assert!(service.retained_output(&info.id).is_ok(), ...)

6. HOW THE TESTS ARE MADE DETERMINISTIC
================================================================================

  - No fixed `sleep` is used as a synchronisation primitive anywhere. Two
    helpers only: `poll_until(cond)` (5 ms steps, 20 s hard deadline) and the
    `wait_for_*` family built on it, each failing with the state it observed.
  - Exits are SEQUENCED, not timed: each shell blocks on `read` from its own pty
    and is released with a `write`. That is what makes "exit order is the exact
    reverse of creation order" structurally true rather than disk/CPU dependent.
  - The 30-session cap test needed `wait_for_exit_or_eviction`, not
    `wait_for_exit`: once more than 25 have exited, the earliest exits are
    ALREADY GONE, so demanding to observe every `exited` status races the cap the
    test exists to prove. Evicted implies exited (eviction is only ever triggered
    from `record_exit`), so the weaker wait is the correct one. First run failed
    exactly here — recorded below as a real finding, not smoothed over.
  - The coalescing/eviction and buffer RULES are unit-tested as pure functions
    (42 lib tests, 0.01s, cannot flake); the integration tests only confirm the
    wiring. That split is why the fast tests are the thorough ones.

TWO GENUINE FAILURES FOUND AND FIXED DURING VERIFICATION (not smoothed over)

  (a) `assert_eq!(service.list().len(), 30)` failed with left: 26, right: 30.
      Cause: the first version spawned `exit N` children, which exit while the
      create loop is still running, so the cap began evicting before all 30
      existed and "30 created, then all exited" was never true. Fixed by gating
      every session so all 30 provably coexist first — which is what the
      acceptance criterion actually describes.
  (b) `wait_for_exit` then timed out at 20s with `Err(NotFound)`: the session it
      was waiting on had already been evicted. Fixed with the weaker wait above.

  Both were test defects, not implementation defects, but both were cases where a
  weaker assertion would have passed while proving less.

8. UTF-8 STRATEGY FOR THE RING
================================================================================

  Truncating a byte ring at an arbitrary offset splits multi-byte code points,
  and the first thing a client does with `replay` is decode it as text. After any
  discard the head advances past UTF-8 continuation bytes (`0b10xxxxxx`), bounded
  at 3 steps because a UTF-8 sequence is at most 4 bytes.

  The bound is load-bearing: a PTY also carries BINARY output, where a
  "continuation byte" is just a byte, so an unbounded scan would empty the whole
  buffer looking for a lead byte that never comes. Asserted by
  `realignment_is_bounded_on_binary_output`: 32 bytes of 0x80 into an 8-byte
  buffer retains exactly 5, i.e. at most three bytes are given up.

  Not oc-llm's `Utf8StreamDecoder` (crates/oc-llm/src/sse.rs:24-91): that one
  holds an incomplete TRAILING sequence pending the next chunk, which is the
  right shape for a stream that must decode to `String` in order. A ring stays
  bytes (a terminal replay is bytes, escape sequences and all) and truncates at
  the HEAD, so it is the mirror-image problem. Recorded in decisions.md.

  Asserted end to end: `multibyte_output_survives_truncation_without_replacement_
  characters` drives 400 iterations of "中文测试内容" through a 1,000-byte buffer
  and requires `std::str::from_utf8(&retained)` to be Ok. The oracle cannot make
  this claim — it counts BUFFER_LIMIT in UTF-16 code units and `slice()`s a
  JavaScript string (pty.ts:218-221), so it can split a surrogate pair.

11. POST-REVIEW FIX — `Ended` could overtake the reader (product bug)
================================================================================

Verification found a real correctness bug in the first commit of this task. Fixed
in src/, not in the test. This section supersedes the counts in section 5.

THE BUG
  `spawn_reader` and `spawn_waiter` were two OS threads with no synchronization.
  `child.wait()` returns as soon as the process dies, while the bytes the child
  wrote microseconds earlier are still in the kernel's pty buffer. So the waiter
  could publish `PtyOutput::Ended` before the reader had drained the pty.

  `Ended` is the stop signal — every consumer stops there, including wave 9's
  `GET /pty/:ptyID/connect`. Consequence: every short-lived command could
  silently lose its last output. A user runs `ls` and intermittently sees
  nothing. The bytes were in the scrollback the whole time, which is why every
  boundedness and retention assertion passed.

THE FIX (crates/oc-pty/src/session.rs)
  `DrainGate { drained: Mutex<bool>, signal: Condvar }` on `SessionShared`. The
  reader latches it AFTER its loop, so the latch means "every chunk is already
  queued". The waiter:

      let exit_code = child.wait().ok().map(|s| s.exit_code());   // reap FIRST
      if !shared.drain.wait_for_drain(DRAIN_GRACE) { tracing::debug!(...); }
      if shared.mark_exited(exit_code) { on_exit(&owned, exit_code); }

  - `child.wait()` stays AHEAD of the drain wait, so a slow drain never delays
    the reap. Covered by `dropping_the_service_terminates_and_reaps_every_child`.
  - Bounded at `DRAIN_GRACE = 500ms`: a grandchild can hold the pty open, and an
    unbounded wait would defer the exit, the retention eviction, and every
    subscriber's `Ended` for the grandchild's whole lifetime. Exceeding it is
    logged, not silent.
  - A separate mutex from `SessionState`: the waiter blocks on the gate, and
    blocking on the state mutex would stall `ingest` — the very thing it awaits.
    No path takes both, so there is no order to invert.
  - The latch is released if the reader thread fails to spawn, so an exit does
    not pay the full grace waiting for output that cannot come.
  - `mark_exited`'s single-delivery guard is untouched; the wait sits in front.

REGRESSION TEST
  `a_subscriber_that_stops_at_the_end_event_has_seen_every_byte`
  64 concurrent sessions (128 threads), each gated then released together, each
  attached at `Tail` with capacity 4096. The loop BREAKS ON `Ended` AND NEVER
  READS PAST IT — reading afterwards would test the buffer instead of the
  ordering and would pass against the bug. `Lagged` is asserted to be 0 so a
  shortfall cannot be blamed on backpressure. Byte-exact, not marker-based.

  Why 64 sessions and not one: the race is decided by scheduler latency alone.
  The obvious single-session test PASSED 5/5 against the reverted fix — it cannot
  fail. The test has to create the contention itself.

MEASURED: on Linux the pty hangs up when its session leader exits
  Probed while testing the bound. Once the spawned child (the pty's session
  leader) exits, the master read ends in ~5 ms REGARDLESS of what descendants do
  with the slave fd. Verified with `sleep &`, `nohup`, `setsid`, `trap "" HUP`,
  and `setsid`+`trap`: all ended in ~5 ms, and output the survivor wrote a second
  later was never retained in any variant.

  So `DRAIN_GRACE`'s timeout branch is NOT reachable from an integration test on
  Linux. It is tested where it is deterministic — four `DrainGate` unit tests, two
  of which use a ten-minute grace so that returning `true` can only mean the
  latch/notify was observed (timing out would hang the test rather than fail it).
  `a_grandchild_holding_the_pty_open_cannot_defer_the_exit` asserts the integration
  property that is real: the exit is published promptly and the child is reaped.

  Side effect worth knowing for wave 9: a background process started from a
  terminal loses its output when the terminal's shell exits. That is the kernel's
  behaviour, not something this crate can change.
