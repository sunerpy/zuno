task-c4 / opencode-rust (zuno)
=========================================================================
缺陷：crates/oc-cli/tests/plugin_models.rs 的
failing_auth_loader_is_disabled_and_models_lists_models_with_a_diagnostic
只因本机工具布局才通过；CodeBuild runner 上 stderr 为空、断言失败。

分支 task-c4，worktree /config/workspace/ProdDir/AI/oc-wt/c4，
基线 origin/main = ea3096f，CARGO_TARGET_DIR=/tmp/opencode/c4。

-------------------------------------------------------------------------
1. 根因（实测，非推断）
-------------------------------------------------------------------------
测试用 .env_clear() 构造密闭环境后写死两个只在本机成立的值：
    .env("PATH", "/usr/bin:/bin")
    .env("MISE_DATA_DIR", "/config/.local/share/mise")

被测插件是 .mjs，必须有 node/bun 才能跑。实测本机：
    $ command -v node  -> /config/.local/share/mise/shims/node
    $ ls /usr/bin/node /bin/node /usr/bin/bun
      ls: cannot access '/usr/bin/node': No such file or directory
      ls: cannot access '/bin/node':     No such file or directory
      ls: cannot access '/usr/bin/bun':  No such file or directory

生产发现顺序（crates/oc-plugin/src/js/runtime.rs:141-176 discover_runtime）：
    PATH  ->  BUN_INSTALL/bin/bun  ->  $MISE_DATA_DIR/installs/<rt>/latest/bin/<rt>
          ->  $XDG_DATA_HOME/mise/...  ->  $HOME/.local/share/mise/...
所以 PATH=/usr/bin:/bin 一定找不到 runtime，本机唯一命中的是写死的
MISE_DATA_DIR。别的机器上该目录不存在 -> 插件从未启动 -> 无 diagnostic ->
断言对着空 stderr 失败。测试此前的“通过”完全是本机布局的偶然。

-------------------------------------------------------------------------
2. 修法
-------------------------------------------------------------------------
保留 .env_clear() 的密闭意图，改为向子进程显式交出**本机实际存在**的
runtime 目录：调用生产的 oc_plugin::discover_runtime（与子进程自己用的是同
一函数，两侧对“什么算 runtime”不会分歧），取其所在目录，前置到
SYSTEM_PATH_BASE = ["/usr/bin", "/bin"] 之前。仍是单一目录 + 系统基座，
不是环境里的 ambient PATH，密闭性未放松。MISE_DATA_DIR 全部删除。

runtime 缺失时的行为（关键验收点，绝不静默通过）：
  * plugin_models.rs 三个子进程测试：js_runtime_or_skip() 打印
    "SKIPPED <test>: no JavaScript runtime found ..." 并 return。
  * plugin_models.rs 两个 in-process 测试：同一 guard，同样可见 skip。
  * tool_turn.rs / session_mutation.rs：js_runtime_path() 以 expect 明确
    panic，消息含 MissingJsRuntime{searched:"bun, node"} 与所属套件名。
顺带证据：同时删掉的 XDG_CACHE_HOME=/config/.cache 并非承重项——真实
antigravity/kiro 测试在删除后仍全部通过（插件路径由 config 里的
installed_antigravity() 提供，不经 XDG_CACHE_HOME）。

【为什么不由本任务修，明确越界报告】
这一层属于 C-3 已在处理的同一缺陷族，而非本任务的 node/PATH 缺陷：
  * issues.md 记录 C-3 的 Defect G = agent_differential.rs 的 BinaryNotFound，
    Defect H = skill_differential.rs 的两处直接 Oracle::discover；两者都改走
    oc_testkit 的 pinned_oracle_or_skip 并登记进
    oc-testkit/tests/no_pinned_oracle_paths.rs 的中央路由清单。
  * 本层 3 项 BinaryNotFound 是同一形状的第三例（Defect I）。
  * 修它需要 (a) 调用/可能调整 crates/oc-testkit/src/oracle.rs，
    (b) 把文件登记进 no_pinned_oracle_paths.rs 的中央清单——前者在本任务的
    禁改清单内，后者是 C-3 的中央门禁，两者都会与 C-3 正在合并的改动冲突。
  * 第 4 项 real_user_config_capture 更是**刻意**硬失败：源码与 panic 文案都写明
    「criterion-2 的机器特定输入不可用时必须可见失败」，compat_suite.rs（同在
    禁改清单内）承载 criterion 2 的判定。把它从 hard-fail 改成 skip 是对
    criterion 2 取证口径的策略决定，不是可移植性 bugfix，超出本任务授权。
因此按交接指示「新失败出现即是进展；诊断清楚，超范围就报告而不是强行转绿」，
本任务不动这些文件，不把这 4 项失败算作自己的结果，也不声称拿到了 Test 全绿。

建议的修法（留给 C-3 或后续任务，保持与 G/H 一致）：
  三项 Oracle::discover 改走 pinned_oracle_or_skip，并把
  crates/oc-config/tests/differential.rs 加入 no_pinned_oracle_paths.rs 清单；
  real_user_config_capture 的 hard-fail 语义需先与 criterion 2 的取证要求对齐，
  由用户裁定是保留硬失败（则 CI 上该 job 永远红）还是降级为可见 skip。
