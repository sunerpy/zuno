   survives a false blanket switch.

The full error chain a reporter would render:

    tool todowrite received invalid arguments
      -> invalid type: integer `0`, expected one of "high", "medium", "low"

  ToolError variant : InvalidArgs { tool: "todowrite", source }
  is_model_correctable(): true
  rows written      : 0 (asserted — a rejected call persists nothing)

Same shape for a numeric status (`a_numeric_status_is_refused_the_same_way`):
    -> invalid type: integer `1`, expected one of "pending", "in_progress", "completed", "cancelled"

Why the message reads that way: serde's DERIVED enum decoder reports only
`invalid type: integer 0, expected variant identifier` — the allowed values do not
appear. `TodoStatus`/`TodoPriority` therefore hand-write `Deserialize` over one
`EnumVisitor` whose `expecting` line enumerates the permitted strings, with explicit
`visit_u64`/`visit_i64` arms so every numeric spelling routes through it.

DELIBERATE DIVERGENCE FROM THE ORACLE, PINNED BY A TEST
------------------------------------------------------
Upstream declares both fields as bare `Schema.String` with the allowed values only in
the *description* (packages/schema/src/session-todo.ts:6-16), so upstream ACCEPTS
`priority: 0` and writes it to the text column verbatim. This port refuses it. The
schema also advertises the permitted values to the model, which upstream's does not —
`todo::tests::the_schema_advertises_the_permitted_values_to_the_model` fails if that
is ever loosened back. Field descriptions are still upstream's word for word.

PART 5 — `position` ORDERING AGAINST THE REAL `todo` TABLE
===============================================================================
Fixture: a real file database, `oc_db::migration::apply` (the byte-compatible upstream
schema), one seeded `project` and two seeded `session` rows. A file rather than
`:memory:` because `Pool` opens a connection per checkout and a plain in-memory
database is per-connection — the second checkout would find no tables.

Written list (5 items spanning every status and priority value):
  alpha   in_progress high
  bravo   pending     medium
  charlie pending     low
  delta   completed   high
  echo    cancelled   low

Rows read back with an explicit `ORDER BY position ASC`
(`a_todo_write_persists_rows_with_position_matching_the_array_index`):

  content   status       priority  position
  --------  -----------  --------  --------
  alpha     in_progress  high             0
  bravo     pending      medium           1
  charlie   pending      low              2
  delta     completed    high             3
  echo      cancelled    low              4

`position` == the item's index in the array the model sent. Asserted as an exact
vector equality, not element-wise, so an off-by-one or a constant would fail.

Supporting assertions, each its own test:
  the_position_column_is_what_carries_the_order_not_the_insert_sequence
      Reads with NO `ORDER BY`, sorts the positions, asserts exactly [0,1,2,3,4] —
      no gaps, no duplicates. A store writing a constant would break the PK; a store
      relying on natural row order would pass the ordered test by coincidence.
  reading_the_list_back_through_the_store_recovers_the_array_order
      Round-trips through `SqliteTodoStore::list`, which is the API a caller uses.
  a_shorter_second_list_does_not_collide_with_the_primary_key
      5 items -> 2 items. The PK is `(session_id, position)`, so without the
      delete-first strategy this is `UNIQUE constraint failed: todo.session_id,
      todo.position`. Passes, and the old rows are gone rather than merged.
  an_empty_list_deletes_every_row_for_the_session
      `todos: []` is a CLEAR, not a no-op — upstream returns early AFTER the delete
      (session/todo.ts:34).
  a_write_is_scoped_to_its_own_session
      Two sessions, independent lists. The delete is scoped by `session_id`, which
      comes from ToolContext and never from the arguments.
  the_timestamp_columns_are_populated_because_they_are_not_null
      `time_created` and `time_updated` are NOT NULL with no SQL default; both are
      written, and equal, from one `now_millis()` per batch.

THE FOREIGN KEY IS ENFORCED, NOT DECORATIVE
-------------------------------------------
  the_foreign_keys_pragma_is_actually_on_for_a_pooled_connection
      `PRAGMA foreign_keys` reads back 1 on a checked-out connection. Verified rather
      than assumed: the pragma's default varies by SQLite build, which is exactly why
      oc-db sets it explicitly (oc-db/src/lib.rs:14-22). Without this assertion the
      next test could pass for the wrong reason on one build and fail on another.
  a_write_for_an_unknown_session_is_refused_by_the_foreign_key
      Writing for `ses_does_not_exist` fails with ToolError::Failed whose chain
      contains "foreign key"; 0 rows written.
  deleting_a_session_cascades_its_todos_away
      DELETE the session -> its 5 todos are gone. `ON DELETE CASCADE` is live.
  a_stored_value_this_port_would_not_write_is_named_rather_than_coerced
      A row with `priority = 'urgent'` (which the TypeScript binary would accept)
      read back as TodoStoreError::UnknownValue { field: "priority", value: "urgent",
      position: 0 } — named, not silently coerced, because guessing which enum an
      unknown string meant would corrupt the user's list. This is the shared-database
      case: a `.db` the TS binary has also written to can contain such values.

The `todo` table DDL was NOT touched and no migration was added.

PART 7 — WHAT WAS NOT VERIFIED, AND WHAT THE PLAN GOT WRONG
===============================================================================
NOT VERIFIED
  - The `question` round trip against a live client. There is no event bus or HTTP API
    in this crate, so the transport is the `QuestionAsker` seam and the tests drive it
    with `ScriptedAnswers`. Whether a real `app`/`desktop` client renders the request
    correctly is untested here and belongs to the server layer.
  - `plan_exit`'s session mutation. Upstream appends a synthetic user message and text
    part (plan.ts:53-69); that is the `PlanExitHost` seam and `RecordingHost` only
    records the call. The actual message write is the session layer's.
  - The second (permission) gate on `plan_exit`. Measured from the binary and
    documented, but implementing it is oc-permission's and todo 44's, not this task's.
  - Byte-for-byte parity of the rendered `question` output against a live oracle run.
    The format is ported from question.ts:30-36 by reading, and asserted against
    hand-derived strings; no oracle invocation produced a `question` transcript, because
    doing so needs an interactive client.

PLAN CORRECTIONS
  1. "`opencode debug agent <name> --tool` prints the resolved tool list" — it does not.
     `--tool` is "Tool id to execute". The list is the `tools` object of the plain
     `debug agent <name>` call. Todo 44's differential must use that.
  2. "`plan_exit` exposed only under the experimental plan mode with a CLI client" is
     the REGISTRY condition and is not sufficient. A second permission gate keyed on
     the agent (`plan_exit: "deny"` by default, `"allow"` for the `plan` agent) also
     applies; with plan mode on and client cli, `plan_exit` is absent from `build` and
     present on `plan`. Recorded in issues.md.
  3. "`invalid` — determine from the oracle whether it is model-visible at all" — it IS
     model-visible, in every one of the 18 measured configurations, with the
     description "Do not use".
  4. "`todowrite` — determine its condition; do not assume unconditional" — it IS
     unconditional (registry.ts:237, and present in all 18 cases). Its predicate says so
     and is tested across a 28-configuration matrix rather than left implicit.
  5. The plan's `oc-db` DDL quote is accurate; the one thing it omits is that
     `time_created` and `time_updated` are also NOT NULL with no SQL default, so an
     insert that supplies only the five named columns fails.
