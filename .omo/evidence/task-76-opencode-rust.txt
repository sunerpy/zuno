4. THE PERMISSION PROMPT'S THREE RESOLUTIONS
=======================================================================

  views_permission_prompt_resolves_to_once
      highlighted option is Once by default; submit -> ReplyKind::Once, message None
  views_permission_prompt_resolves_to_always_after_confirming
      submit on Always -> DialogStep::Redraw + Stage::ConfirmAlways (does NOT
      resolve); second submit -> ReplyKind::Always
  views_permission_prompt_resolves_to_reject
      end -> Reject highlighted; submit -> ReplyKind::Reject

  Plus the safety properties:
  views_permission_escape_rejects_rather_than_allowing
      escape with Once highlighted still yields Reject
  views_permission_cancelling_the_always_confirmation_decides_nothing
  views_permission_reject_message_is_only_offered_in_a_child_session
  views_permission_reject_message_is_typed_and_carried  -> Some("use rea")
  views_permission_empty_reject_message_is_none_not_an_empty_string
  views_permission_decision_converts_to_the_engine_reply
      PermissionDecision::into_reply() -> oc_permission::PermissionReply

  Vocabulary is oc_permission::ReplyKind {Reject, Once, Always}, read from
  crates/oc-permission/src/types.rs:41-45. Nothing was invented.

5. INCREMENTAL STREAMING PROOF
=======================================================================

  views_streaming_message_renders_incrementally

  Feeds AssistantMessageCreated then four TextDelta events
  ("The", " quick", " brown", " fox"), rendering off-screen after each. Asserts:
    - each delta returns EventResult{redraw:true} (an invisible stream is a bug)
    - frame 1 contains "The" and NOT "quick"
    - frame 2 contains "The quick" and NOT "brown"
    - frame 4 contains "The quick brown fox"
    - every frame's whitespace-stripped text is a PREFIX of the next one, i.e.
      growth, not a re-render from scratch

  Supporting:
  views_streaming_reasoning_and_text_accumulate_into_separate_parts
  views_retry_rollback_discards_the_interrupted_attempt
      StreamEvent::RetryRollback clears the in-flight parts; without it the
      model's answer renders twice
  views_tool_call_walks_pending_running_and_terminal_states
      Pending -> Running -> Error across ToolUseStart / ToolDispatchStarted /
      ToolDispatchCompleted

11. THINGS THE PLAN / SOURCE DISAGREED ABOUT
=======================================================================

a) `help_show` ships UNBOUND. keybind.rs:1024-1030 gives it `keys: "none"`, so it
   is reachable only through the command palette. A help test written against it
   asserted `keys != "(unbound)"` and failed; retargeted to `session_interrupt`
   and a separate test now pins the unbound-by-default fact.

b) The default scroll speed is 3, not 1. util/scroll.ts:26 returns
   `new CustomSpeedScroll(3)`. Getting this wrong is a difference every user feels.

c) The split-diff threshold is EXCLUSIVE (`width > 120`), so exactly 120 columns
   is unified. Tested at both 120 and 121.

d) `space` reaches a dialog only as `dialog.mcp.toggle` — the binding table's sole
   `space` row. A multi-select question needs a toggle key and adding a second
   `space` row would be a keybind conflict the table rejects at construction, so
   the question prompt claims that row and also accepts the raw `' '` as a
   fallback for a user who rebound it.

e) `Dialog::desired_height` originally took only `available`, which made every
   dialog full-height and hid the base behind it. Changed to
   `(content_rows, available)` — the host passes the row count its `lines()` call
   produced, because `lines()` takes `&mut self` and a size query must not mutate.
