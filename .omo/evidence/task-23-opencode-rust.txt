== F. GC BEHAVIOUR, MEASURED ===================================================
oracle parameters: index.ts:23 prune = "7.days"; :300-316 cleanup() = git gc --prune=7.days,
  guarded by exists(gitdir) and enabled(), failure logged and tolerated;
  :761-766 cadence = Effect.delay(1 minute) then Schedule.spaced(1 hour), forkScoped.

measured with real git 2.43.0 (drives the two gc tests):
  1. git gc REPACKS loose objects, unreachable ones into a cruft pack (.mtimes),
     so a vanished loose file is NOT evidence of reclamation. Tests use cat-file -e.
  2. an unreachable object inside the 7-day window survives (repacked, retrievable).
  3. an unreachable object older than 7 days is reclaimed (cat-file -e fails).
  4. the LATEST snapshot tree is reachable via the index cache-tree and always survives;
     a SUPERSEDED tree older than 7 days is reclaimed  => a de-facto 7-day revert horizon.
  5. the store directory, objects/, config and index survive every gc.

== I. DELIBERATE DIVERGENCES ===================================================
1. track/restore report failure instead of swallowing it.
   Oracle logs and continues, so track() can return "" as if it were a hash and restore()
   can be a silent no-op. Both surface as SnapshotError here: a silently-empty snapshot
   hash breaks revert much later, far from the cause. Failures the oracle tolerates BY
   DESIGN (partial add, failed diff, failed gc) stay tolerated and logged.
2. SnapshotError is crate-local, not an oc-error variant. oc-error has no process/exec
   variant, its aggregate Error is not #[non_exhaustive], and oc-paths set the precedent
   with PathsError. Misfiling a git failure as ToolError::Failed would claim a model tool
   failed. No anyhow anywhere; oc-error's guard test still passes.
3. The store lock is in-process only (one Mutex per git dir, mirroring the oracle's
   Semaphore keyed by gitdir). Cross-process exclusion is Git's own index.lock; adding a
   second lock file would invent a protocol the TypeScript binary does not speak.
