THE THREE PARAMETERIZED custom() LOADERS  (why Spec must carry per-provider data)
--------------------------------------------------------------------------------
custom() at provider.ts:168 returns 22 loaders. Three of them route to a different
SDK surface per call, which a registry keyed only by provider name cannot express:

  selectAzureLanguageModel            provider.ts:154-160
    walks chat -> responses -> messages -> languageModel, gated on a useChat flag.
    Its endpoint is assembled from a resourceName resolved from provider options,
    then env, then stored auth -> Spec.base_url + Spec.api_version + Spec.surface.

  selectBedrockMantleLanguageModel    provider.ts:162-166
    model ids openai.gpt-oss-safeguard-20b and -120b go to chat(); everything else
    to responses(), falling back to languageModel().
    Routing is per MODEL, not per provider -> CompletionRequest.surface, plus
    Spec.region for the signer.

  github-copilot getModel             provider.ts:225-239
    prefers model.api.endpoint when the catalog declares one; else /^gpt-(\d+)/
    with N >= 5 and not gpt-5-mini -> responses(); else chat().
    Also per MODEL -> CompletionRequest.surface.

Hence ApiSurface { Default, Chat, Responses, Messages } appears in two places:
Spec.surface for a choice fixed at construction, CompletionRequest.surface for a
choice made per model. Asserted by
registry_spec_expresses_every_parameterized_provider_in_the_oracle.

PROVIDER TRAIT -- final method list (narrow by design; the reference has ~30)
--------------------------------------------------------------------------------
pub trait Provider: std::fmt::Debug + Send + Sync + 'static {
    fn id(&self) -> &str;
    fn capabilities(&self) -> Capabilities;
    fn stream(&self, request: CompletionRequest) -> ProviderStream<'_>;
}

Three methods. Debug is a supertrait, not a method, so it adds no width; it is
required because a Result carrying a provider must be printable when it turns out
to be the wrong branch.

Capabilities is one struct rather than five predicate methods:
  reasoning, tool_calls, prompt_cache, attachments, sampling_params
Each field exists because a named downstream todo branches on it (28, 29, 30, 31).

Deliberately excluded, with the owner of each:
  model listing / metadata / cost / token limits  -> catalog.rs, todo 26
  authentication and credential refresh           -> oc-auth, todo 24
  retry, backoff, compaction decisions            -> oc-error Recovery, todo 2

  SSE framing and incremental UTF-8 decoding      -> sse.rs, todo 27

THE COMPOSITION-ROOT SIGNATURE  (what todos 29, 30, 94, 95, 96 must satisfy)
--------------------------------------------------------------------------------
pub type Factory     = Arc<dyn Fn(Spec) -> FactoryOutcome + Send + Sync>;
pub type FactoryOutcome = Result<Arc<dyn Provider>, Declined>;
pub type Composition = fn() -> ProviderRegistry;

oc-cli implements Composition exactly once. Each provider todo adds ONE call inside
that single function and changes nothing else in the workspace:

  // infallible: the provider always constructs
  registry.register("anthropic", |spec| {
      Arc::new(oc_provider_anthropic::Anthropic::new(spec))
  });

  // fallible: construction may decline, and must say why
  registry.register_fallible("github-copilot", |spec| {
      let token = load_token().ok_or(Unavailable::MissingCredential)?;
      Ok(Arc::new(oc_provider_openai::Copilot::new(spec, token)?))
  });

Declined has From<Unavailable> and From<ProviderError>, so ? works for both arms.
