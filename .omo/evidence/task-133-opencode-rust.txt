SEAM 14 FOUND — the chat-context model encoding does not match the declared shape

While proving the header injection I probed which field the hook matches on. The
hook resolves `input?.model?.providerID ?? input?.provider?.info?.id`
(`dist/plugin.js:390`). With `model.provider_id = "kiro-auth"` and
`provider.info.id = "not-kiro"` the plugin injects NOTHING:

  PROBE model-only-match -> {}

So `input.model.providerID` never reaches the plugin. `chat_context_value`
(`crates/oc-plugin/src/jsonrpc.rs:1219-1236`) serializes `ResolvedModel` with
Rust field names, so the plugin sees `provider_id`, not the `providerID` upstream's
type declares. `chat.message` in the SAME codec already spells it `providerID`
(`jsonrpc.rs:972`), so the two encodings disagree with each other — this is an
internal inconsistency, not a design choice. Kiro survives only on its
`?? provider.info.id` fallback; a plugin reading only `model.providerID` would
silently never fire, and `chat.params` has the same input shape.

NOT FIXED HERE, deliberately: correcting `chat_context_value` changes the plugin
wire contract for both `chat.params` and `chat.headers` and needs its own todo
with upstream key-set verification. It is instead PINNED where a gate sees it —
the test asserts the model-only match currently injects nothing, with a message
saying that closing the seam is a fix and this assertion must then be updated. A
recorded seam that fails on repair beats a comment nobody reads.

F2 BLOCKER 2 — the PTY expiry assertion passed for the WRONG REASON

Two independent defects, both fixed.

DEFECT 1, the one F2 reported. The fixture issued the stale ticket with
`TicketScope::for_session`, whose `directory` is `None`, while `pty::connect`
redeems with `Some("/repo")` (`crates/oc-server/src/api/pty.rs:144-163`). The
route returned 403 on the SCOPE MISMATCH, so the assertion held with expiry
enforcement removed entirely.

DEFECT 2, found while fixing the first and not previously reported.
`prune_expired` (`crates/oc-pty/src/ticket.rs:194-201`) sweeps from the FRONT
only. That is CORRECT in production — `issue` always stamps `Instant::now()`, so
the queue is ordered oldest-first and a non-expired front implies no expired
entry — but a back-dated ticket pushed behind a fresher one escapes the sweep
entirely. My first fixed draft did exactly that and returned 400: the ticket
minted earlier in the test was still outstanding in front of it. This is NOT a
production defect and is NOT reported as one; it is a constraint the test must
respect to be meaningful, and `consume_at` performing no per-entry age check is
what makes the FIFO invariant load-bearing.

THE FIX. The expiry block now runs LAST, after the single-use and replay
assertions have drained the queue, and it asserts `tickets().is_empty()` first so
the stale ticket is provably the oldest — the ordering production guarantees. A
`probe` ticket is then issued with the hand-built production scope and redeemed
successfully (400 at the WebSocket upgrade, not 403), which PROVES the scope
matches production before the stale ticket is trusted to fail for expiry. Only
then is the back-dated ticket redeemed and required to be 403.

  MUTATION G (THE REQUIRED DEMONSTRATION). `prune_expired` replaced with a no-op:

    fn prune_expired(_entries: &mut VecDeque<Entry>, _ttl: Duration, _now: Instant) {}

  The FIXED test fails:

    thread 'api_pty_connect_requires_a_single_use_unexpired_ticket_without_echoing_it'
    panicked at crates/oc-server/tests/api.rs:1073:5:

    refused. Its scope matches the route exactly — proven by the probe above — so
    expiry is the only thing left that can reject it, and removing `prune_expired`
    turns this into a 400.
