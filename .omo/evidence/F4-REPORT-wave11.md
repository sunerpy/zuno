## Todo 162 — advertised Copilot endpoint propagation

**Judgment: BLOCKER; the wave-10 production-supply defect remains open at the actual JavaScript plugin boundary.**

- The lower layers are real improvements. `ModelApi` now has the closed optional `endpoint` field (`crates/oc-llm/src/catalog/resolved.rs:78-104`); catalog/config merge preserves it; `model_spec` publishes it under the wire `api.id`; and compatible-provider request/stream selection can dispatch either Responses or Chat. The two named replay tests both pass when actually selected: `cargo test -p oc-cli --offline production_copilot_advertised_responses_beats_a_heuristic_hostile_id` and the inverse `...advertised_chat...` each ran one test and passed.
- Those tests do **not** cross the production plugin boundary they claim to model. `plugin_resolved_wire_spec` serializes a Rust `ResolvedModel`, mutates `api.endpoint`, deserializes the same Rust shape, and calls `replace_provider_models` directly (`crates/oc-cli/src/cmd/turn_tests.rs:280-335`). That serialization emits the Rust-only key `provider_id` because `ResolvedModel.provider_id` has no `serde` rename/alias (`crates/oc-llm/src/catalog/resolved.rs:47-76`). It never invokes `HandleModelLoader`, imports JavaScript, or consumes the SDK's modern `providerID` spelling.
- The real bridge simply calls `serde_json::from_value::<ResolvedModel>` on each JavaScript-returned model and skips any decode failure (`crates/oc-plugin/src/js/bridge.rs:445-487`). A production-binary reproduction placed a valid provider hook in `.opencode/plugin/provider.js`; its model used the modern SDK shape with `providerID: "github-copilot"` and `api.endpoint: "responses"`. Running the audited binary's real `models github-copilot --verbose` composition root with pinned catalog/config produced: `skipped a plugin model this host could not decode ... model=mai-code-alias error=missing field provider_id`, followed by `Provider not found: github-copilot`. Thus the advertised endpoint never reaches catalog replacement, `model_spec`, or wire dispatch.
- This is not hypothetical spelling preference. The product already emits `providerID` to plugin-facing message codecs (`crates/oc-plugin/src/jsonrpc.rs:972`), while the bridge comment explicitly says a plugin returns the SDK `Model` shape (`crates/oc-plugin/src/js/bridge.rs:467-470`). The installed real Kiro plugin happens to spread back the host's own provider-model input (`.../opencode-kiro-auth/dist/plugin.js:426-443`), masking the mismatch; a provider that constructs an upstream-shaped model is dropped.
- The issues ledger overstates the proof when it says the replay tests use “the same resolved-plugin shape used by `HandleModelLoader`” (`.omo/notepads/opencode-rust/issues.md:7254-7260`). They use the bridge's desired Rust shape, not its actual JavaScript input contract. The plan required preservation through **plugin model resolution** and production-path metadata (`.omo/plans/opencode-rust.md:1419-1421`), so a direct Rust serde round trip cannot close the fifth-layer blocker.

**Required closure:** decode the modern plugin `Model` shape at `HandleModelLoader` (including `providerID`, and any other SDK/Rust naming differences) and add a production-path JavaScript provider-hook test whose returned advertised endpoint survives real host import/call, catalog replacement, `model_spec`, and recorded wire dispatch in both precedence directions. No product fix was made in this audit.

## Final disposition

**REJECT.** Todos 163 and 164 faithfully close their stated scope, the plan contains 164 checked implementation todos, all 17 declared divergences are legitimate choices, and every mandatory workspace gate is green. Those facts do not override the production-boundary failure in Todo 162: a JavaScript provider hook returning the modern SDK `Model` shape is rejected because `HandleModelLoader` requires Rust's `provider_id` instead of accepting plugin-facing `providerID`. Consequently the advertised endpoint cannot traverse the required plugin-resolution layer, and the passing production-wire tests bypass exactly that seam by injecting a Rust `ResolvedModel` directly. This violates the frozen Todo 162 acceptance criterion and leaves wave 10's scope-fidelity blocker open.

The minimum closure is the one stated above: accept the modern plugin model wire shape and prove both endpoint-precedence directions through a real JavaScript hook, catalog replacement, `model_spec`, and recorded provider dispatch. This audit intentionally makes no product, test, plan, or documentation fix.
