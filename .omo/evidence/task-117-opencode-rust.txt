# Task 117 — accept the user's real configuration so `debug config` matches upstream

Worktree `/config/workspace/ProdDir/AI/oc-wt/t117`, branch `task-117`.
Oracle source pinned at `/config/workspace/ProdDir/AI/opencode` @ `aefaf140c1` ("sync release
versions for v1.18.13"). Released binaries used: `1.18.12` (named by the todo) and `1.18.15`
(what `Oracle::discover()` finds on this host).

## 1. The offending key

    theme

Named exactly once, at the top level of `/config/.config/opencode/opencode.json:7`:

    "theme": "system",

Recovered by a throwaway probe calling `Config::from_json_str` on a **copy** of the live file
(`/tmp/t117/opencode.json`); the user's own file was never opened for writing:

    PROBE ISSUE path=["theme"] detail=unrecognized key

`theme` is the only offending key in that file, which matches the `(1 issue(s))` count.
Its two siblings in upstream's handling — `keybinds` and `tui` — are absent from this
particular user's file but are the same case, and were fixed together.

## 2. What upstream actually does with it, and where that is written

`theme` is **not** in upstream's top-level schema. Searching the schema module finds nothing:

    $ grep -rn "theme|keybinds" packages/core/src/v1/config/config.ts
    (no matches)

The only mention anywhere in the config layer is a delete, one function above the loader:

    packages/opencode/src/config/config.ts:53-61
      function normalizeLoadedConfig(data: unknown) {
        if (!isRecord(data)) return data
        const copy = { ...data }
        const hadLegacy = "theme" in copy || "keybinds" in copy || "tui" in copy
        if (!hadLegacy) return copy
        delete copy.theme
        delete copy.keybinds
        delete copy.tui
        return copy
      }

and it is applied to the parsed document **before** validation, at the single call site:

    packages/opencode/src/config/config.ts:227
      const data = ConfigParse.schema(ConfigV1.Info, normalizeLoadedConfig(parsed), source)

`ConfigParse.schema` is the function whose `topLevelExtraKeys` check
(`packages/opencode/src/config/parse.ts:40-53,74-78`) throws `unrecognized_keys` — the very
check this port mirrors. Because the delete runs first, the three keys never reach it.

So upstream's behaviour is neither "accept into the schema" nor "ignore unknown keys
generally": it is **strip these three named keys, then reject every other unknown key**. That
distinction is the whole fix. The keys moved to `tui.json`, and the migration that relocates
them (`packages/opencode/src/config/tui-migrate.ts`) skips any directory that already has a
`tui.json` — this user has `/config/.config/opencode/tui.json`, which is precisely why `theme`
has sat in `opencode.json` indefinitely while upstream kept quietly ignoring it.

## 4. How the fix was narrowed

Three changes, all bounded by a three-name list:

* `crates/oc-config/src/schema.rs` — `LEGACY_TUI_KEYS = ["theme","keybinds","tui"]`, and three
  `LegacyTuiKey` fields (a ZST that swallows any JSON shape via `IgnoredAny`, `skip_serializing`).
  Deliberately **not** added to `KNOWN_TOP_LEVEL_KEYS`: that list is the set that survives the
  merge, and these must not survive it.
* `crates/oc-config/src/schema/parse.rs` — `reject_unknown_top_level_keys` exempts exactly
  `LEGACY_TUI_KEYS`. `deny_unknown_fields` stays on `Config`; no arm of the schema was widened.
* `crates/oc-error/src/config.rs` — `ConfigError::report()`, so a validation failure names its
  keys. `Display` is unchanged (four existing tests pin its single-line form).

Wired into the four config-discovery call sites a user can reach: `debug.rs`, `agent.rs`,
`models.rs`, `mcp.rs`. `turn.rs` was left alone — todo 115 owns it this wave.

Evidence the narrowing is real, not a relaxation:

* `every_unrecognized_top_level_key_gets_its_own_issue` now uses the **near-misses** `themes`
  and `keybind`, so a substring or prefix match in the exemption would fail it. Previously this
  test used `theme` and `keybinds` — it was asserting the defect.
* `the_legacy_exemption_covers_exactly_three_keys` pins the list and asserts none of the three
  joined `KNOWN_TOP_LEVEL_KEYS`.
* `deprecated_top_level_keys_are_not_accepted` (pre-existing) still rejects `mode`, `layout`,
  `autoshare`.
* End to end, through the binary:

      $ XDG_CONFIG_HOME=/tmp/t117/badcfg OPENCODE_PURE=1 ./target/debug/opencode-rust debug config
      config file /tmp/t117/badcfg/opencode/opencode.json failed validation (1 issue(s))
        themes: unrecognized key
      BAD_RUST_EXIT=1

  and the oracle agrees it is invalid on the same tree:

      $ XDG_CONFIG_HOME=/tmp/t117/badcfg 1.18.12/opencode debug config
      Error: Configuration is invalid at /tmp/t117/badcfg/opencode/opencode.json
      ↳ Unrecognized key: themes
      BAD_TS_EXIT=1

## 5. Todo 10's deprecated-form rejections — verified, not assumed

`legacy_the_tui_exemption_rejects_nothing_the_deprecation_pass_owns` (new, in
`crates/oc-config/tests/legacy.rs`) checks both directions:

* none of the three exempt keys is a `DeprecatedForm` (`inspect_config` returns empty for each,
  while `from_json_value` accepts each) — so the exemption cannot have swallowed one;
* `ModeBlock`, `Layout`, `Autoshare`, `Reference`, `AgentTools`, `AgentMaxSteps` each still get
  detected by `inspect_config` **and** rejected by `check_config` with a non-empty key path.

The two `DeprecatedForm` variants that are filesystem-shaped (`ContextFile`, `TomlConfig`,
`ModeDirectory`) and `AuthPromptCondition` are covered by the pre-existing per-form unit tests
in `src/legacy/tests.rs`, which pass unchanged.

Also confirmed through the binary that a deprecated form still fails:

      $ XDG_CONFIG_HOME=/tmp/t117/depcfg OPENCODE_PURE=1 ./target/debug/opencode-rust debug config
      config file /tmp/t117/depcfg/opencode/opencode.json failed validation (1 issue(s))
        mode: unrecognized key
      DEP_RUST_EXIT=1

Pre-existing gap noted, **not** in this todo's scope: `mode` is caught by the schema's
`unrecognized key`, not by `legacy::check_config`'s actionable "use `agent.build` with
`mode: \"primary\"`" message, because discovery does not call the legacy pass. `legacy.rs`'s own
module doc says the pass "must therefore run before the strict parse". That wiring is untouched
by this change (behaviour identical before and after) and belongs to whoever owns the legacy
pass's integration.

## 6. The differential

New matrix case `real-user-global-config` in `crates/oc-config/tests/differential.rs` places the
live file, byte-for-byte, as the global config layer and compares against the released binary:

    real-user-global-config: oracle(installed-binary .../1.18.15/opencode, reports 1.18.15,
                                    pinned source 1.18.13 @ aefaf140c1)
      normalization rules available: (none — byte-exact comparison)
      normalization masked: nothing
      result: identical

Byte-exact, with no normalization masking anything. The case carries `OPENCODE_PURE=1` because
the fixture's `plugin` list resolves real npm plugins that inject `agent`/`command`/`skills`
into the oracle's merged config; that is plugin loading, a separate surface, and `OPENCODE_PURE`
is this suite's existing lever for it (`pure_env_and_cli_flag_disable_external_plugins_without_suppressing_config`).
`REQUIRED_COVERAGE` gained `real-user-config` and `legacy-tui-keys` so the case cannot be
dropped silently.

## 7. Why every test passed while the binary rejected a live config

The checked-in fixture `crates/oc-config/tests/fixtures/user-config.json` was a copy of the
user's file **with `theme` removed**, and `crates/oc-config/tests/legacy.rs` documented the
omission as harmless:

    /// Its one difference from the live file is the `theme` key, which
    /// v1.18.13 does not define and which is not a deprecated form either way.

Both halves of that sentence are true and the conclusion was still wrong: v1.18.13 does not
define `theme`, and it also does not reject it. The fixture was friendlier than reality, which
is the same shape as the two earlier seams (`OPENCODE_MODELS_PATH` injected by every test, a
legacy database no test ever opened). `theme` is now restored to the fixture, and
`the_real_user_config_deserializes` asserts it is present in the input and absent from the
parsed output — so removing it from the fixture again fails the test rather than hiding the bug.
