2. THE DESCRIPTION, VERBATIM (extracted from the compiled `DESCRIPTION` constant)
--------------------------------------------------------------------------------
Save durable facts to persistent memory that survive across sessions. Memory is injected into every future session, so keep entries compact and high-signal.

HOW: make ALL your changes in ONE call via an 'operations' array (each item: {action, content?, old_text?}). The batch applies atomically and the char limit is checked only on the FINAL result — so a single call can remove/replace stale entries to free room AND add new ones, even when an add alone would overflow. The response reports current/limit chars and confirms completion; one batch call finishes the update, so don't repeat it. Use the bare action/content/old_text fields only for a single lone change. 'old_text' is a short substring that must identify exactly one entry.

WHEN: save proactively when the user states a preference or correction, or you learn a stable fact about their environment, this codebase's conventions, or how they want to be worked with. Priority: user preferences & corrections > project conventions & commands > tool quirks you had to rediscover. The best memory stops the user repeating themselves.

IF FULL: the write is rejected with the current entries shown. Reissue as ONE batch that removes or shortens enough stale entries and adds the new one together.

TARGETS: 'global' = habits that travel with the user into every repository (their preferences, corrections, working style, tool quirks). 'project' = rules that belong to this repository only (its build and test commands, layout, conventions, gotchas). A repo rule filed globally is paid for in every unrelated session; a travelling habit filed per-project is relearned in every checkout.

SKIP: trivial or obvious information, facts you could rediscover in seconds, raw data dumps, and anything about the work in flight — task progress, completed-work logs and temporary TODO state belong to the goal tools (get_goal/update_goal) and session_search, not here. A reusable procedure belongs in a skill, not memory.
  1969 chars. Structure carried from memory_tool.py:1152: HOW / WHEN /
  IF FULL / TARGETS / SKIP. Two sections diverge:
    TARGETS — retargeted onto this project's real scopes (global agent

      profile store does not exist here, so naming it would be a lie the

    SKIP   — keeps 'task progress, completed-work logs, temporary TODO
      state' and points them at BOTH owners this project has: the goal
      tools (get_goal/update_goal, todo 68) and session_search (todo 102).
      The reference names only session_search.

5. WHAT "PER TURN" IS KEYED ON
--------------------------------------------------------------------------------
  ToolContext carries session_id, message_id, call_id (crates/oc-tool/src/context.rs
  :169-190). The breaker keys on **session_id**, with an explicit
  `MemoryTool::reset_for_turn(session_id)` hook for the engine to call at a turn
  boundary. Why not the other two:

    call_id     unique per call -> the counter would reset on every attempt and the
                breaker could never fire.
    message_id  the assistant message, and oc-engine mints a NEW one for every step
                (crates/oc-engine/src/loop.rs:620-624). A model only retries after
                reading the refusal, which costs another step, so keying here would
                ALSO reset on every attempt — while still passing a test that reuses
                one id. A false green, which is worse than no breaker. The breaker
                test deliberately passes msg_1..msg_4 to prove the streak survives
                changing message ids.
    session_id  stable across every step of a turn, so a streak survives to be
                counted.

  The reference is keyed the same way without saying so: its counter lives on a
  MemoryStore that is "one instance per AIAgent" (memory_tool.py:148-149) and the
  per-turn property comes from an external reset_consolidation_failures() call at
  the turn boundary (:176-178). Until the engine calls reset_for_turn, the streak is
  still bounded by the other reset the reference relies on: a SUCCESSFUL write
  clears it (:704-706), because the cap counts a stuck loop, not a lifetime tally.
  `a_success_clears_the_streak_so_the_cap_counts_a_stuck_loop` pins that.

6. WHY A TRIPPED BREAKER IS STILL A SUCCESSFUL TOOL RESULT
--------------------------------------------------------------------------------
  crates/oc-engine/src/dispatch.rs:496-515 — `joined_result` maps Ok(Ok(output)) to
  ToolDispatchResult::success and Ok(Err(ToolError)) to
  ToolDispatchResult::error(...). Either way the turn loop persists a tool result and
  keeps going (loop.rs:751-790); a ToolError does not abort the turn. But it DOES
  mark the result `is_error: true` and replaces the tool's own body with a rendered
  error string, which would discard the usage figures and the entries the model needs.
  So every store refusal is returned as Ok(ToolOutput) carrying `success: false` — the
  refusal is information the model reads, not a failure of the call. The only Err path
  is an unusable call SHAPE (ToolError::InvalidArgs), where there is nothing to report
  about memory at all and the model must correct the call.

7. THE DUAL SCHEMA SHAPE — schemars could NOT express the either/or
--------------------------------------------------------------------------------
  `operations` array XOR bare action/content/old_text is a JSON Schema `oneOf`.
  schemars 1.2.2 derives no `oneOf` across sibling fields of one struct, and Todo 38
  forbids hand-writing the schema. Resolution, as the plan's fallback directs: all
  operation fields are Option<...>, `target` stays required, and
  MemoryParams::operations() validates at run time, returning ToolError::InvalidArgs
  whose CAUSE is oc-memory's own MemoryError::MalformedOperation — so a missing
  `content` is worded identically whether it came from the tool or from apply_batch
  (todo 98 exposed Operation::parse for exactly this).

  Derived schema facts asserted by `the_schema_is_derived_and_advertises_both_shapes`:
    required                      ["target", "intent"]      (intent injected centrally)
    target                        oneOf const global|project
    operations                    type ["array","null"]
    operations.items.required     ["action"]
    operations.items.action       oneOf const add|replace|remove
    operations.items.content      type ["string","null"]
    operations.items.old_text     type ["string","null"]

  A second test, `no_maintainer_rationale_rides_in_the_wire_schema`, asserts no
  "Todo 38"/"memory_tool.py"/intra-doc-link text reached the schema: schemars copies
  rustdoc verbatim, and the params types' docs are billed to the model on every
  request for the whole session. Maintainer rationale therefore lives in module docs,
  which do not ship.

10. GAPS AND DISAGREEMENTS, STATED PLAINLY
--------------------------------------------------------------------------------
  * `reset_for_turn` has NO CALLER. Nothing in oc-engine calls it, because wiring the
    engine's turn boundary to a tool instance is outside this todo's crate boundary
    (the plan forbids touching any crate but oc-tools). Consequence today: the streak
    resets on a successful write and on a new session, but not at a plain turn
    boundary — so three failures in turn 1 followed by one in turn 2 trips the breaker
    a turn early. That is strictly the safe direction (it stops retrying sooner, never
    later), and the reference has the identical dependency on an external caller. The
    hook, its contract and this gap are documented on the method.
  * `cargo test -p oc-tools memory` reports 20 in the lib and "0 passed; 5 filtered
    out" for tests/memory.rs, because the filter matches test names and the
    integration tests are named for their behaviour. Reported rather than papered over
    by stuffing "memory" into five test names. `--test memory` runs all 5, green.
  * lsp_diagnostics was unusable, exactly as todo 98 recorded: the LSP tool refuses
    paths outside the request cwd (/config/workspace/ProdDir/AI/opencode-rust) and
    this work is in the oc-wt/t100 worktree. `cargo clippy --workspace --all-targets`
    at 0 warnings plus a clean workspace build is the stronger gate and was used.
  * CodeGraph MCP was uninitialized in this worktree as forewarned; Read/Grep/Glob
    throughout. context7 not needed.
  * Nothing in oc-memory or oc-tool needed changing. The API todo 98 shaped for this
    todo (`current_entries()`, `is_consolidation_failure()`, `Operation::parse`,
    `Usage: Display`) was sufficient as delivered.
