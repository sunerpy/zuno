WHERE PRESET DATA LIVES, AND WHY THE GREP TEST STILL PASSES
-----------------------------------------------------------------------------
Preset SHAPE is code (`PresetDocument` / `PresetBody` / `ModelPreset` /
`ModelChoice`). Preset DATA is configuration and ships nowhere in this crate.
`oc-agent` contains zero model ids and zero preset assets.

That is not a dodge of the acceptance test, it is what slim actually does. Slim's
five presets (`src/cli/providers.ts:11-56`) look like shipped policy until you
follow the consumer: MODEL_MAPPINGS is read only by `generateLiteConfig`
(`:79-137`), which WRITES the presets into the user's config file at install
time. The runtime then reads `config.presets` (`src/index.ts:209-215`) and never
the constant. The installer's table is a scaffold, not a policy — a shipped
preset in the binary *is* CATEGORY_MODEL_REQUIREMENTS with better manners and
rots identically.

`PresetDocument::parse_json` accepts both shapes:
  * flat, exactly what slim's installer emits — {agent: {model, variant}}, and a
    bare "provider/model" string is accepted as a model with no variant;
  * structured — {"agents": {...}, "categories": {...}} — the only way to declare
    categories.
A body is read as structured exactly when it holds an `agents` or `categories`
key. `PresetBody`'s Deserialize is HAND-WRITTEN rather than #[serde(untagged)]:
the flat shape is a superset of the structured field set, so an untagged enum
reads {"worker": ...} as a structured body with two defaulted empty maps and
silently drops every entry. Test: the_flat_shape_cannot_be_silently_swallowed_by_the_structured_one.

EFFORT — todo 31's canonical levels, and the ported Claude-budget SHAPE
-----------------------------------------------------------------------------
`read_variant` parses a preset's `variant` with ReasoningEffort::from_str first.
A canonical level goes straight to oc_llm::effort::resolve_effort — no second
mapping table anywhere in oc-agent.
  a_canonical_variant_resolves_through_todo_31s_levels covers all 6 levels
  (off/low/medium/high/xhigh/max) for ProviderFamily::OpenAi and asserts
  ResolutionSource::GenericMapping plus the exact option object.
  a_presets_variant_reaches_effort_resolution_unchanged takes the variant a
  preset chose and shows it produce Google's thinkingConfig.

The ported shape of omo's dist/index.js:28822-28829 (32,000-token budget for one
vendor's older models, deliberately `{}` for its newer ones "so native variants
take over"): the branch is taken on a CATALOG fact, never a model name.
`declared_variants` lifts ResolvedModel::variants (keyed by NAME) into todo 31's
DeclaredVariants (keyed by canonical EFFORT), so a model that declares "max"
wins over the generic family mapping; a model that declares nothing gets the
budget shape. Test: a_catalog_declared_level_wins_over_the_generic_family_mapping
asserts DeclaredVariant for the first and a numeric budgetTokens for the second.
A non-canonical variant name the model DOES declare (slim ships one —
`variant: 'thinking'`, src/cli/providers.ts:48) is handed back verbatim as
EffortOutcome::ModelVariant with the catalog's own option object; nothing is
synthesised. A name nobody declares is EffortOutcome::Inherit + a diagnostic.
omo needs a new hand-written `is…OrLaterModel` predicate per model release; this
needs none.

A REAL FALSE POSITIVE THE CRATE-WIDE SCAN FOUND (and the fix)
-----------------------------------------------------------------------------
Todo 63's predicate only ever saw RENDERED PROSE (agent descriptions, boundaries,
envelopes). Pointing it at SOURCE immediately failed on builtin.rs:49:

  builtin.rs:49: ``dist/index.js:24475`` looks like a model id.

A source citation `path/file:line` is a two-segment path with digits on the right
— indistinguishable from `provider/model` under the old rule. Fixed by excluding
tokens containing `:` from the `provider/model` branch only: no provider spells a
model with a colon, and the FAMILY branch runs first, so a real id stays caught
however it is punctuated. Pinned in
the_scanner_would_catch_a_model_id_in_this_module, whose benign list now includes
"dist/index.js:24475", "src/cli/providers.ts:11-56" and
"session/session.ts:331-335", and whose positive list still catches six planted
ids assembled from split literals.

This is why the scanner had to MOVE rather than be duplicated: builtin.rs could
not be touched, so the fix had to land in the one shared definition.

FINDINGS / DEVIATIONS
-----------------------------------------------------------------------------
* No config key exists for the preset library. `Config` has `model`,
  `small_model`, `default_agent` and `agent.<name>.{model,variant}` but no
  `preset` / `presets`. Per-agent overrides therefore need NO new key — they read
  the existing ones — but preset selection has no home in oc-config yet.
  `PresetDocument::parse_json` is the seam; wiring it is a one-field addition to
  `Config` that belongs to whoever owns that schema. Recorded in issues.md;
  oc-config was NOT modified.
* Internal agents (compaction/title/summary) resolve like any other agent. The
  engine already owns small_model routing (oc-engine/src/compaction.rs:404) and a
  second answer here would be a place for the two to disagree.
* `AGENTS_KEY`/`CATEGORIES_KEY` are reserved words: a preset cannot configure an
  agent literally named `agents` or `categories`. The cost of accepting the flat
  shape a neighbouring tool already writes.
* Nothing in the plan was wrong. Its four claims about slim and omo all check out
  against the sources: DEFAULT_MODELS is nine `undefined` entries with the quoted
  rationale (constants.ts:26-41); providers.ts:11-56 is five agent-keyed presets;
  AGENTS_MODEL_REQUIREMENTS is at dist/index.js:24467 (plan said 24475 — that is
