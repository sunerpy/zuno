缺陷 A — oxfmt 在 CI 里从未安装
--------------------------------------------------------------------------------
根因  `make fmt-check` → `fmt-oxfmt-check`（Makefile:74-77）显式
      `command -v oxfmt || { echo "oxfmt is required…"; exit 1; }`。
      `grep -c oxfmt .github/workflows/ci.yml` = 0。
修法  `actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0`
      钉 `node-version: "22"`，随后
      `npm install --global oxfmt@0.59.0` + `oxfmt --version`（后者是门禁，不是日志）。

为什么钉 0.59.0 而不是 latest
      本机 pre-commit 钩子实际使用的就是 0.59.0（`oxfmt --version` → `Version: 0.59.0`），
      而 npm 上当时最新是 0.63.0。formatter 换版本可能对已提交文件有不同意见，
      于是 CI 会红在没人改过的文件上。

为什么必须同时钉 Node
      `npm view oxfmt@0.59.0 engines` → `{ node: '^20.19.0 || >=22.12.0' }`，
      且它是 19 个 per-platform native binding 的包装（`@oxfmt/binding-linux-x64-gnu` 等）。
      CodeBuild `aws/codebuild/standard:7.0` 默认 Node 18，`npm install` 对 EBADENGINE
      只 warn 且退出码 0，失败会推迟到两步之后变成 `Cannot find module @oxfmt/binding-…`。

本机验证该机制（不是推断）
      npm install --no-fund --no-audit oxfmt@0.59.0     → added 3 packages in 18s
      ./node_modules/.bin/oxfmt --version               → Version: 0.59.0
      oxfmt --check --ignore-path .oxfmtignore \
        .oxfmtrc.json .pre-commit-config.yaml docs/readme/README.en.md
                                                        → All matched files use the
                                                          correct format（exit 0）
      即 npm 装出来的 0.59.0 与仓库已提交的格式一致。

缺陷 B — `--offline` 是 Makefile 默认值，CI 从不填 registry
--------------------------------------------------------------------------------
根因  Makefile:32 `OFFLINE ?= --offline`，于是 `make release` 展开为
      `cargo build --release -p oc-cli --bin zuno --offline`，冷 runner 上报
      `error: no matching package named 'async-trait' found`
      `note: offline mode (via '--offline') can sometimes cause surprising resolution failures`
      `make: *** [Makefile:132: release] Error 101`。
      `Swatinem/rust-cache`（ci.yml:63,132,152）在冷缓存下恢复不了任何东西；
      ci.yml:69 的 `cargo metadata --locked` 是**在线**的，所以它成功了并掩盖了
      后面全是离线这一事实。
修法  在 `test` 和 `artifact` 各加一步 `cargo fetch --locked`。

为什么不改 Makefile
      `OFFLINE ?= --offline` 对本地离线开发是正确默认值，且 `?=` 已经允许
      `OFFLINE=` 覆盖。缺陷不在默认值，而在「CI 复用共享 make target 时默默继承了
      它的前置假设」。修法应该是在调用 target 前把假设满足，而不是改默认值伤害本地体验。

为什么不带 `--target`
      learnings.md:3526 记录过 `cargo metadata --locked --offline` 会因一个
      Windows-only 传递依赖失败（"attempting to make an HTTP request, but --offline
      was specified"）。不带 `--target` 时 `cargo fetch` 取所有 target 的依赖，
      一次覆盖这个坑。

缺陷 C — 注释与代码矛盾（改了代码，重写了注释）
--------------------------------------------------------------------------------
原状  ci.yml:55-56 注释：「No `toolchain:` input: rust-toolchain.toml pins 1.96.0
      and the components, and naming a channel here would silently override it」
      ci.yml:61 代码：`toolchain: stable`

不能按注释删 input —— 读第三方 action 源码得到的实测结论：
      git clone dtolnay/rust-toolchain @ 6c977a6，读 action.yml：
        :35-39  空值时 `echo "'toolchain' is a required input" >&2; exit 1`
                （GitHub 不强制 required: true，所以 action 自己校验；它不读 toml）
        :96-98  它做的全部事情是 `rustup toolchain install <ver> --profile minimal`
                加 `rustup default <ver>`（后者还带 continue-on-error: true）

所以注释里「会静默覆盖 toml」这句本身也是错的：toolchain 文件优先级高于
`rustup default`，写 `stable` 不会让构建用 stable 编译；真正的失败模式是
**rustfmt/clippy 被装到一条用不上的 toolchain 上**，然后 rustup 还得自动装第二条。

决定  改代码为 `toolchain: "1.96.0"`（与 rust-toolchain.toml 同值，共 4 处），
      注释重写为陈述实测机制。代价是多一处重复字面量 —— 用一行交叉引用注释标出，
      因为没有任何测试绑定 rust-toolchain.toml 与 ci.yml 这两处。

缺陷 D — Windows job：`if:` 开关，不是删，也不是 continue-on-error
--------------------------------------------------------------------------------
约束  `windows-latest` 永远拿不到 runner（run 31868933369：runner_name 为空、
      steps=0、conclusion=failure，一步都没跑，与代码无关）。
      也搬不到 CodeBuild：Windows runner 需要预留容量 fleet，而
      `aws codebuild list-fleets --region cn-northwest-1`
        → InvalidInputException: Unknown operation ListFleets
      即 aws-cn 分区没有 fleet API，只有 LINUX_CONTAINER。

选择  `if: vars.GITHUB_HOSTED_RUNNERS == 'true'`；job 保留定义、保留在
      `ci-success` 的 `needs:` 里；`ci-success` 脚本按 **job 名 + 结果值** 双重枚举
      允许 skipped 的 job。
      当前 `gh api repos/sunerpy/zuno/actions/variables` → {"variables":[],"total_count":0}，
      所以默认就是 skip；额度回来后设一个仓库变量即可恢复硬门禁，无需再改文件。

为什么不用 continue-on-error: true
      它会连真实的 Windows 失败一起吞掉。这里要保住的区分正是「没跑」与
      「跑了但失败」，只有前者可接受。

为什么不用「一律忽略 skipped」
      `cancel-in-progress: true` 下被新 push 取消的 job、或因 `if:` 写错而整体跳过的
      test job，都会因此变绿 —— 那正是 `ci-success` 存在要堵的洞。

门禁逻辑本地验证（把 run: 脚本抽出来直接喂 NEEDS_JSON）
      python3 -c "yaml.safe_load(...)['jobs']['ci-success']['steps'][0]['run']" > gate.sh
      bash -n gate.sh                                            → OK
      windows=skipped, 其余 success                              → exit 0
        "CI passed: 3 of 4 required job(s) succeeded, 1 opt-in job(s) skipped."
      windows=failure, 其余 success                              → exit 1
        "::error … required job 'windows' concluded 'failure', not 'success'."
      test=skipped, windows=skipped                              → exit 1
        "::error … required job 'test' concluded 'skipped', not 'success'."
      即枚举确实是按 job 且按结果的，不是宽泛放行。

一次基础设施故障（非本改动引入，已定位）
    GitHub 的 workflow_job 投递**不重试**（错误文本自带 "giving up after 1 attempt(s)"），
    而 aws-cn 的 CodeBuild webhook 端点不稳：
        08:07:38.008 workflow_job/queued code=502 failed to connect to host   ← Test 的事件
        08:07:38.799 workflow_job/queued code=200
        08:07:45.789 workflow_job/queued code=200
        08:09:18.873 workflow_job/in_progress code=500 context deadline exceeded
    那条 502 丢失后 CodeBuild 从不知道该 job 存在，于是永久卡 queued（runner_name 空、steps=0）。
    同 run 内另两个 job 拿到真实 runner UUID，排除了「接线坏了」。
    失败与突发相关：6 秒内 3 个事件 → 2 失败；单独一个事件（gh run rerun --job）→ 200 且立即派发。
    恢复用的是 cancel + 单 job 重跑；投递重发 API 在本机 token 上返回 404。
    附注：CodeBuild 的 webhook.lastTriggeredAt 在 aws-cn 上恒为 null，即使派发成功 ——
    继承 skill 把它当「唯一干净判据」，在此分区不成立。

缺陷 E — oc-smoke 的请求形状比运行时晚了 8 天（读到了 prelude）
    `8cd05f6` 写 smoke driver 时一次 tool turn = 2 个请求；`3e6730c`（更晚，
    git merge-base --is-ancestor 判定）引入 title prelude，使每次运行先发一个
    **不带工具**的请求。`tool_turn.rs:57-61` 已同步为 1+2=3，`:1122` 明确断言
    prelude 不提供工具，`:1133` 从 captured[1] 读工具 —— 该测试在本机 3519/0 里通过。
    `oc-smoke.rs:305,315` 从未同步，仍断言 2 并把 captured[0] 当 turn 请求，
    于是读到那个按设计就空的 prelude，报出误导性的
    「the assembled tool registry did not reach the provider」。
    本机 100% 复现（与 CodeBuild 逐字一致），故与 CI 环境无关。
    正确修法要同时动 oc-smoke 的下标、把只有 2 个 interaction 的 cassette 扩到 3
    （`release_surface.rs:1217` 正钉死 2），而 cassette 由
    `committed_smoke_cassette_matches_the_oracle_recording` 守着必须**重新录制** oracle。
    手写 cassette 会造出假 fixture —— 那正是这套门禁要防的，故不在本任务内做。

缺陷 F — oc-acp::live_sdk 依赖仓库之外的宿主本地目录，干净机器上必败
    `live_sdk.rs:4-14` 的 sdk_entry() 对 CARGO_MANIFEST_DIR 走 ancestors()，
    逐级找 opencode/packages/opencode/node_modules/@agentclientprotocol/sdk/dist/acp.js。
    仓库内没有该路径，**也没有 submodule**（.gitmodules 不存在、git submodule status 为空）。
    逐级实测命中的是仓库**之外**、worktree 上两级的
        /config/workspace/ProdDir/AI/opencode/packages/opencode/node_modules/…/acp.js
    即一个上游 TypeScript opencode 的平行 checkout。所以本机能过是宿主布局巧合，
    CI 上 ancestors() 找不到 → `.expect()` 直接 panic（不是 skip）。
    两条修法都需要设计决定而非接线：优雅 skip 会把真门禁变成可跳过的门禁；
    在 CI 里 provision 则要回答「按哪个钉住的上游 commit 提供 oracle tree」——
    随手 npm install 一个任意版本会造出假 oracle，与该测试的意义相反。

按任务的「不得为了让 CI 变绿而弱化或删除测试」，这两项均按原样保留为红，
并附完整根因，而不是靠放宽断言换一个绿勾。
