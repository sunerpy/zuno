--------------------------------------------------------------------------------

Reported symptom (both tool_turn tests):

FIRST CORRECTION TO THE PLAN: the failure is NOT deterministic. The plan and
.omo/WORKTREE.md both state "it was the refactor, not a flake". It is BOTH: a
real regression the refactor introduced, whose manifestation is a coin flip.
Measured, 8 consecutive runs of the unmodified tree:

    --- run 2 --- test result: ok. 3 passed
    --- run 3 --- test result: ok. 3 passed
    --- run 4 --- test result: FAILED. 2 passed; 1 failed

    --- run 5 --- test result: ok. 3 passed

    --- run 7 --- test result: FAILED. 2 passed; 1 failed
                  append-only cache violation on turn 2: stable history message 1 changed
    --- run 8 --- test result: ok. 3 passed

2 failures in 8. A second batch of 12 gave 2 more. Roughly 15-25%.

SECOND CORRECTION TO THE PLAN: `resolve_session`'s signature change from
`&RunArgs` to `&TurnPlan` is NOT the cause. Line-by-line against
`git show main:crates/oc-cli/src/cmd/run.rs`, the port is behaviour-preserving.
`persist_user_message` is byte-identical apart from taking `now` from the caller.

RUNTIME EVIDENCE. Instrumented `hydrate_session`, `assistant_message` and
`persist_user_message` and captured a failing run (instrumentation since removed;
`rg TEMP-T105 crates/` is clean):

    TEMP-T105 open      now=1786118122726
    TEMP-T105 user      id=msg_76add12001954584ae90cea5389d0c3c created=1786118122766
    TEMP-T105 hydrate step=1 idx=0 id=msg_76add12001954584ae90cea5389d0c3c role=User      created=1786118122766
    TEMP-T105 assistant id=msg_392e2cf52b5c46dd85a8526509079dd0_0001 created=1786118122766
    TEMP-T105 hydrate step=2 idx=0 id=msg_392e2cf52b5c46dd85a8526509079dd0_0001 role=Assistant created=1786118122766
    TEMP-T105 hydrate step=2 idx=1 id=msg_76add12001954584ae90cea5389d0c3c    role=User      created=1786118122766
    TEMP-T105 assistant id=msg_392e2cf52b5c46dd85a8526509079dd0_0002 created=1786118122770
    append-only cache violation on turn 2: stable history message 1 changed

Read the two hydrations. Step 1 saw [User]. Step 2 saw [Assistant, User] — the
assistant's reply sorted AHEAD of the prompt it answers. Both carry
`created=1786118122766`: the SAME millisecond.

`MessageStore::messages_for_session` (crates/oc-db/src/message.rs:669) orders

    ORDER BY time_created ASC, id ASC

The tie rule is correct and faithful to upstream (`message-v2.ts:95-96`) — but
UPSTREAM'S IDS ARE TIME-ORDERED IDENTIFIERS AND THIS PORT'S ARE RANDOM UUIDS
(`prefixed_id` = `format!("{prefix}_{}", Uuid::new_v4().simple())`). So a
same-millisecond tie is broken by whichever random hex string sorts first. Here
`msg_392e...` < `msg_76ad...`, so the reply won and went first.

Turn 1's request prefix was [system, user]. Turn 2's was [system, assistant, ...].
Index 1 changed from the user message to the assistant message, and todo 31's
append-only tracker (crates/oc-llm/src/cache.rs:153) correctly refused it.

WHY THE REFACTOR CAUSED IT, AND WHY `main` IS SAFE. `main` computes ONE `now` at
the top of `run::execute` (run.rs:102) and passes it to `persist_user_message`.
Between that call and the first `assistant_message()` it does the whole tool
assembly: `tool_runtime::assemble` walks the config, builds the registry, applies
the permission rules. That work reliably spans a millisecond boundary, so the
stamps differed and the tie never occurred. `main` was not correct — it was lucky,
and the luck was load-bearing.

`TurnHost` splits open-time from drive-time (correctly — the interactive surface
must resolve everything before entering raw mode). Assembly now happens in
`open()`, and `drive()` persists the prompt and calls `run_turn` back to back with
nothing in between. The gap closed, the tie appeared, and the coin started
flipping. Measured above: `open now=…726`, prompt at `…766` (40 ms of assembly),
first assistant also `…766` — 0 ms later.

The stderr line `[get_weather] failed: get_weather error` is EXPECTED, not a
symptom: the cassette's recorded call names a tool this runtime does not have, and
`tool_turn.rs:39-48` documents that as the point of that test. Present on `main`
too.

--------------------------------------------------------------------------------
2. THE FIX
--------------------------------------------------------------------------------

Not a suppression of the check. The check is right; the write order was wrong.
The port must stop relying on random ids to express "later".

crates/oc-db/src/message.rs — the ordering contract's owner gains two items:

  * `MessageStore::latest_time_created(session_id) -> Option<i64>`
    One statement, answered from `message_session_time_created_id_idx` without
    reading a `data` blob.
  * `created_after(now, latest) -> i64`
    `now.max(latest + 1)`, saturating. Also fixes a backwards clock.

crates/oc-engine/src/loop.rs — `assistant_message` takes `history` and stamps
    `created_after(now_millis(), max(history.time_created))`. The reply cannot tie
    or precede anything already in the session, whatever the clock says.

crates/oc-cli/src/cmd/turn.rs — `TurnHost::drive` reads `latest_time_created`
    and stamps the prompt with `created_after`. Needed for the multi-turn case
    todo 105 introduces: prompt n+1 is submitted immediately after turn n stored
    its reply, which is the same collision one level up.

4. tests/tui_turn.rs MEETS THE PTY CRITERION — AFTER ONE FIX
--------------------------------------------------------------------------------

It does drive the REAL binary (`CARGO_BIN_EXE_opencode-rust`) under a REAL pty via
`script -qefc`, the same mechanism as `perf/workload.rs:114-123`. Not in-process.

But as inherited it FAILED, for an environment reason, not a wiring one:

    thread '…' panicked at crates/oc-cli/tests/tui_turn.rs:266:5:
    the assistant's reply never reached the screen; the turn ran but the events did not
    transcript:
    ^[[?1049h^[[?1000h…^[[?25l^[[39m^[[49m^[[59m^[[0m^[[?25l…   (28 empty frames, no text)

Note WHICH assertion fired: the captured-request assertions above it PASSED, so
the turn ran. Only the paint was missing. Measured cause:

    $ script -qefc "sh -c 'echo stty: $(stty size); echo tty: $(tty)'" /dev/null < /dev/null
    PROBE stty: 0 0
    PROBE tty: /dev/pts/7

`script` copies its window size from its own stdin. Under a test harness that is a
pipe and has none, so the pty is real, `is_terminal()` is true, and the viewport is
0x0 — every frame draws nothing. Fixed by sizing the pty from inside the launched
command, which is the only place that can:

    stty rows 40 cols 120; <program> --pure --prompt … --model … --auto

    $ script -qefc "stty rows 40 cols 120; …" /dev/null < /dev/null
    PROBE stty: 40 120

NOTE FOR TODO 88: `perf/workload.rs` spawns with `.stdout(Stdio::null())` and
`.stdin(Stdio::piped())`, so its pty is 0x0 too. That is FINE and must not be
"fixed": the TS oracle baseline was measured through the same 0x0 pty, so the
comparison is apples-to-apples. It only means neither side pays for rendering.
`perf/**` is frozen and was not touched.

8. THE OTHER ACCEPTANCE CRITERIA
--------------------------------------------------------------------------------

PERMISSION PROMPT resolves a real `PermissionAsk`, not `HeadlessApproval`:
    `rg HeadlessApproval crates/oc-cli/src` → only run.rs:37 and its definition
    in tool_runtime.rs. The tui hands the dispatcher a `PermissionBroker`, which
    parks a `PermissionRequest` on a `oneshot` and is answered by
    `PermissionBridge`, a component in the tree, via todo 76's `PermissionPrompt`.
    `AutoApproval` is a separate type used only under `--auto`. Four tests in
    cmd/tui_permission_tests.rs, all passing.

STATUS STRIP never reports idle during a turn. `StatusView` gains `running`,
    `IDLE`/`WORKING` and `is_running()`; `mark_running()` covers the window
    between a submitted prompt and `TurnStarted`; `reset(false)` on
    `TurnCompleted`/`TurnInterrupted` also clears the finished turn's agent and
    model so the row stops describing a turn that is over. Was untested — added
    `views_status_strip_never_reads_idle_while_a_turn_is_under_way`, checking all
    three moments. The typed-prompt transcript in section 5(b) shows the live
    `idle → working → reply` progression.

ONE DRIVER, TWO SURFACES: `cmd/turn.rs` is the only composition root. `run.rs`
    shrank 445 lines. Both surfaces import `TurnHost`/`TurnOptions`/`TurnPlan`/
    `SessionChoice`; neither re-implements `run_turn` or the assembly.

EVENT LOOP NOT BLOCKED: the prompt leaves the screen as a `String` on a bounded
    channel (capacity 1, so a second submission is a visible refusal rather than a
    silent queue); `drive_turns` holds the only `TurnHost` on its own task and
    publishes `TurnEvent`s back on the channel `App` already drains.

FROZEN INPUTS UNTOUCHED: `git status --short` lists no path under
    `crates/oc-testkit/src/perf/` or `docs/perf-methodology.md`.

10. WHAT THE PLAN GOT WRONG
--------------------------------------------------------------------------------

1. "The same two tests pass on `main` … so this is a regression" — right about the
   regression, wrong that the failure is deterministic. It is a ~15-25% coin flip,
   and both the plan and .omo/WORKTREE.md assert "not a flake". A single green run
   of `tool_turn` would have looked like a clean bill of health. Anyone
   re-verifying this path must run it repeatedly, not once.
2. "the most likely cause" being `resolve_session`'s `&RunArgs` → `&TurnPlan`
   change: not the cause. That port is behaviour-preserving. The cause is the
   removal of ~40 ms of tool-assembly work from between the two writes, which is
   a change in TIMING, not in logic — invisible to the line-by-line diff the plan
   proposed.
3. "Check whether that failure [`get_weather error`] is itself a symptom" — it is
   not. It is the recorded cassette calling a tool this runtime does not have, by
   design, and it appears on `main` too.
4. `tests/tui_turn.rs` did meet the PTY criterion structurally but did not pass:
   `script`'s 0x0 window size made every frame empty. The plan listed the file as
   present without noting it was red.
5. Not in the plan and needed for todo 88: W-soak submits its follow-up turns by
   TYPING into the pty, a path `--prompt` never exercises. Added a second test for
   it. Had it been broken, todo 88 would still have been blocked after a green
   `--prompt` test.
