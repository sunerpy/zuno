1. WHAT WAS MISSING, AND WHY THE OLD PROOF WAS HALF A PROOF
--------------------------------------------------------------------------------
Criterion 1's round trip was proved at two much weaker points:

  a) compat_suite.rs::journal_round_trip_through_the_real_binary_does_not_replay_
     migrations — opens an EMPTY Rust database and compares the `migration` table.
     It passed throughout the entire life of this project's worst defect.

  b) compat_suite.rs::a_session_written_by_this_port_is_decodable_by_the_real_binary
     and oc-cli/tests/rollback.rs — ask the release to LIST a session this port
     wrote. Real, and the correct fix for todo 115, but "can be listed" is one verb
     out of five.

Neither asks the question a user asks. A session can be listable and still lose its
transcript; a transcript can be readable and still not grow; a binary can read the
other's rows and still drop them when it continues. Every one of those failures is
invisible to (a) and (b).

The gap is now closed by four tests, all over ONE persisted session per test, with
the two real programs alternating against ONE `OPENCODE_DB` file.


2. THE TWO DIRECTIONS — STEPS AND ASSERTIONS
--------------------------------------------------------------------------------
Both run inside a single `ScriptedEnv` with `DbChoice::Absolute(<one path>)`. That
is structural, not conventional: neither binary is given a way to reach a second
database, so "the same session" cannot silently become "a session each" after a
later edit. `SharedWorld` owns it (session_interop.rs:319-352).

--- THE SAME SESSION, NOT TWO: how that is proved rather than asserted

  Three independent facts, any one of which fails if a fixture ever forks:
    * `SharedWorld` exposes one absolute `OPENCODE_DB` to both runners;
    * `session_ids()` is compared to `vec![session]` — an exact vector equality, so
      a second row fails by value, not merely by count;
    * the continuing binary's OUTBOUND provider request replays the other binary's
      user turn. A forked session would replay nothing.

--- TRANSCRIPT GROWTH is asserted on STORAGE, in TWO units

  `TranscriptSize::grew_from` requires `messages > earlier.messages` AND
  `parts > earlier.parts` (session_interop.rs:395-404), read straight out of SQLite.
  Strictly, on both units, on purpose: a run that appended a message row but no part
  rows persisted a turn with no content, and "readable" would still hold.


3. THE DECODE PROOF — WHY IT IS THE WIRE AND NOT AN `export` SUBSTRING
--------------------------------------------------------------------------------
each_implementation_replays_every_turn_the_other_one_wrote drives THREE turns
alternating ORACLE → RUST → ORACLE over one session, then asserts on the requests
the binaries sent:

  chat request 1 (oracle) : 1 replayed user turn
  chat request 2 (rust)   : 2 replayed user turns, INCLUDING the oracle's turn 1
  chat request 3 (oracle) : 3 replayed user turns, INCLUDING this port's turn 2

  Measured user-turn counts: [1, 2, 3]
  Measured sizes:            2msg/4parts → 4msg/6parts → 6msg/10parts

This is the strongest available form of "the opposite implementation can decode what
the other wrote": the bytes did not merely parse, they came back out of the decoder
and onto the wire. Assertion 3 also requires request 3's replayed history to be
strictly longer than request 2's, so a release that dropped only the FOREIGN turn
would still fail — a test that checked only the newest turn would not notice.


4. THE FAILURE TEST — a row shape only one implementation can decode
--------------------------------------------------------------------------------
the_oracle_refuses_a_session_model_shape_only_this_port_could_decode

  The ORACLE creates the database first, so its own `project` row scopes the listing.
  (A fabricated project id makes `session list` exit 0 with an EMPTY result, which
  silently disarms the test. Recorded because a first draft of the sibling test in
  compat_suite.rs did exactly that.)

  Then one session is written through the production writer `oc_db::session::create`
  with the MESSAGE spelling in the SESSION column:
      {"providerID":"test","modelID":"test-model"}

  Measured against 1.18.15:
      release exited exit status: 1
      stderr = Error: Unexpected error / Expected string, got undefined

  The test then rewrites the same row through `oc_db::session::model_reference` and
  requires the release to exit 0 AND name the row — so the failure above is
  attributable to the SHAPE and not to the row's mere presence.

  This is what stops every assertion in sections 2 and 3 from being vacuous.

6. A GENUINE DIVERGENCE FOUND WHILE DOING THIS, NAMED RATHER THAN NORMALISED
--------------------------------------------------------------------------------
For one assistant turn the release persists FOUR parts and this port persists TWO:

  release 1.18.15   user|text  assistant|step-start  assistant|text  assistant|step-finish
  this port         user|text  assistant|text

Reproduced on the `run` path both inside a git repository and outside one, so this is
NOT the "step-start only carries a snapshot" case; production data holds 218,899
`step-start` rows whose blob is literally `{"type":"step-start"}`
(.omo/notepads/opencode-rust/learnings.md:2076).

It does not break interoperability — every assertion in sections 2-4 holds across it,
in both directions, which is itself a useful finding. It is a production-behaviour
difference and therefore out of scope for a test todo, and `docs/divergences.toml`
was deliberately NOT edited (that surface is being changed by todo 135 in parallel;
touching it here would create a merge conflict for no gain).

What was NOT done is to let the assertions quietly absorb it. The exemption is
stated in the test module's own doc comment, with its measurement, so a reader of a
green run knows this file does not claim part-shape parity. An invisible exemption is
what F4 rejected twice; a visible one is acceptable.

RECOMMENDATION: this belongs in a follow-up todo — either implement the two parts or
declare the divergence and bump `DECLARED_COUNT` (currently 13 entries).
