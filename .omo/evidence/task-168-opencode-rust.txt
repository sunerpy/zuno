Initial dispatch and load audit
-------------------------------
- `HookInvocation` has 21 variants and `PluginRuntime` wires all 21 production boundaries.
- Four are not turn-fatal callback dispatches in the adapter:
  - `tool`, `auth`, and `provider` are resource collectors; `HookBus` currently returns `Ok` without calling `Plugin::call`.
  - `dispose` logs its error during shutdown and does not fail an active turn.
- The remaining 17 callback dispatch sites all propagate `HookBus::dispatch` errors to their caller:
  `config`, `event`, `chat.message`, `chat.params`, `chat.headers`, `permission.ask`,
  `command.execute.before`, `tool.execute.before`, `shell.env`, `tool.execute.after`,
  `experimental.chat.messages.transform`, `experimental.chat.system.transform`,
  `experimental.provider.small_model`, `experimental.session.compacting`,
  `experimental.compaction.autocontinue`, `experimental.text.complete`, and `tool.definition`.
  Sixteen use `map_err(|error| error.to_string())`; `shell.env` wraps the same error in
  `ToolError::Failed`. Thus a bridge/write-back failure from any of these 17 can abort the
  surrounding lifecycle instead of being contained.
- Existing out-of-process and WebAssembly plugins already implement the documented containment
  contract internally: they disable themselves, retain a typed `PluginDiagnostic`, and return
  success to `HookBus`.
- JavaScript host transport failures are also retained by `JsHost`, but `JsPlugin::call` currently
  discards every `call_hook` error with `let Ok(result) = result else { continue; }`. Bridge-side
  failures after a successful callback (`invocation_output` / `apply_hook_output`) escape to
  `HookBus`, which wraps them as `PluginError::Hook`; this is the todo 151 truncation path that
  reaches the fatal adapter mappings.

  diagnostics. `load_one` fully starts and builds the plugin, then returns it in

  `docs/plugin-authoring.md:37-40` says an incompatible npm plugin is skipped. Therefore the
