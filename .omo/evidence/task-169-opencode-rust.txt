Recorded shapes established before implementation changes
---------------------------------------------------------

1. Antigravity recovery prompt

Source: `/config/.cache/opencode/packages/opencode-antigravity-auth@1.6.0/node_modules/opencode-antigravity-auth/dist/src/plugin/recovery.js:120-130`.

The installed plugin maps every unmatched tool-use id to:

    {
      type: "tool_result",
      tool_use_id: id,
      content: "Operation cancelled by user (ESC pressed)"
    }

and submits the resulting array as `body: { parts: toolResultParts }` to
`client.session.prompt`. The callsite explicitly uses `@ts-expect-error` because
the published prompt-part type omits `tool_result`, then treats a resolved call
as recovery success and catches every rejection as `false`.

3. OMO session create

Sources:
- `/config/.cache/opencode/packages/@sunerpy/oh-my-openagent@4.21.0/node_modules/@sunerpy/oh-my-openagent/dist/index.js:135030-135045`
- the second installed call at the same file `:143073-143088`

The recorded model object is exactly:

    {
      id: input.categoryModel.modelID,
      providerID: input.categoryModel.providerID,
      ...(input.categoryModel.variant ? { variant: input.categoryModel.variant } : {})
    }

inside a create body that also carries `parentID`, `title`, and `permission`,
with `query.directory`. The second call uses the same `{id, providerID,
variant?}` shape. This agrees with the repository decoder contract at
`crates/oc-server/src/api/session.rs:883-892` (`ModelRefBody.id`) and the measured
database contract at `crates/oc-db/src/session.rs:207-227`; the existing test's
`{providerID, modelID}` shape is the incompatible message spelling.

Pre-change causes
-----------------

- `tool_result` reaches `prompt_body` in `compat_v1.rs:1110-1137`; its match
  accepts only `text`, `file`, `agent`, and `subtask`, so the installed payload
  takes the catch-all `unsupported v1 prompt part type` path and returns HTTP 400.
- `v1_session_summarize` extracts `Json<Value>` into `_body` and never reads it;
  `api::session::compact` builds `SessionCompactExecution.model` exclusively
  from `session.model` (`api/session.rs:773-797`).
- `v1_session_create` already passes `body.model` through unchanged. The product
  path can persist the installed `{id,providerID,variant?}` contract, but the
  route regression uses `{providerID,modelID}` and never consumes the stored
  value through `session_model`, hiding corrupt fixture state.

Pre-implementation route regressions
------------------------------------

- `compat_v1_omo_session_create_persists_and_consumes_the_recorded_model_shape`
  passed with the exact `{id,providerID,variant}` object. It additionally read
  the raw session row and prompted the created child without an explicit model;
  the production `session_model` decoder supplied `deepseek/deepseek-chat` to
  the executor. This establishes that the adapter itself already passed the real
  shape and that the defect here was the prior friendly fixture/absent consumer.
- `compat_v1_omo_summarize_uses_the_recorded_body_model` failed as intended.
  The recorded request returned 200, but the captured real compact execution had
  `model: None`; expected was the body-selected `deepseek/deepseek-chat`.
- `compat_v1_antigravity_recovery_tool_result_reaches_the_prompt_executor`
  failed as intended with HTTP 400 versus 200. No prompt execution occurred.

Implementation
--------------

- Session create now deserializes `model` as the existing `ModelRefBody`
  (`id`, `providerID`, optional `variant`) before converting it back to the
  opaque JSON stored by the shared create handler. The production session-row
  decoder remains unchanged and strict.
- Summarize now deserializes a typed `{providerID,modelID,auto?}` body and calls
  the shared compact execution path with the body-selected model. The compact
  execution contract now carries `automatic`; the shipped server executor sends
  that flag through `compact_requested`, so `auto: true` reaches the compaction
  marker rather than being merely parsed by the adapter.
- The prompt adapter accepts the installed `tool_result` variant, requires both
  string `tool_use_id` and string `content`, and uses the cancellation content as
  the text that starts the recovery turn. The core turn loop's existing
  `repair_missing_tool_outputs` pass repairs unmatched stored tool calls before
  it hydrates that turn, preserving the plugin's recovery purpose without
  weakening the core prompt schema.
