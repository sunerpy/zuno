2. Measured production schema depth

The schema sources under `crates/oc-tools/src` were read before selecting a bound:
`registry.rs` supplies the real built-in order and visibility projection; `todo.rs`,
`memory.rs`, `question.rs`, `batch.rs`, and `apply_patch.rs` define the deepest nested
`JsonSchema` inputs. In particular, `TodoWriteParams -> Vec<TodoItem> -> enum` and
`MemoryParams -> Vec<MemoryOperation> -> enum` produce the nested `oneOf` objects.

For an exact production measurement, the no-op hook dumped the `ToolDefinition` value
it received from the real binary before read-back. A temporary measurement-only copy
of the embedded shim used depth 64 so every currently visible definition could finish;
both `shim.mjs` and `tool_turn.rs` were backed up first and restored byte-clean after
the probe. Container depth is zero-based and counts each JSON object/array edge, exactly
as `encode` does. Results for the real turn's ten visible tools:

  invalid:   definition 3, schema 2
  bash:      definition 4, schema 3
  read:      definition 4, schema 3
  glob:      definition 4, schema 3
  grep:      definition 4, schema 3
  edit:      definition 3, schema 2
  write:     definition 3, schema 2
  webfetch:  definition 5, schema 4
  todowrite: definition 8, schema 7
  memory:    definition 8, schema 7

The measured maximum is definition-root depth 8. The first deepest path is exactly:

  /parameters/properties/todos/items/properties/priority/oneOf/0

`memory` independently reaches the same depth at:

  /parameters/properties/operations/items/properties/action/oneOf/0

Thus `MAX_DEPTH = 8` replaces a real object because the check fires at `depth >= 8`.
The selected production cap will be 16: twice the measured requirement, leaving eight
full object/array levels of margin while retaining a finite walk. Raising the cap is
not the structural fix: markers will also carry whether the capped object is the same
host-supplied boundary object or a boundary introduced/replaced by the plugin, and the
Rust guard will refuse both without accusing/disabling the plugin for host-origin loss.

4. Implementation and fixed-state targeted results

The two defects are addressed separately rather than hiding one with the other:

- Production depth: `MAX_DEPTH` is 16, double the measured maximum of 8. The cap is
  still finite and applies to callback values and every returned argument, so arbitrary
  plugin graphs remain bounded.
- Attribution and future cliffs: before invoking the callback, shim records object
  identities that are already at the host argument's cutoff boundary. On read-back it
  classifies a cutoff as `host` only when the exact same object remains at the exact
  JSON Pointer; replaced/new objects are `plugin`. The authoritative classifications
  are returned in response sideband outside the plugin callback's values, so a plugin
  cannot forge `$source: "host"` to bypass refusal.
- `bridge.rs` restores only sideband-proven host cutoff markers from the original Rust
  argument before deserialization/write-back. That preserves bytes instead of merely
  suppressing an accusation. A sideband-proven plugin cutoff is still refused; a
  marker literal without matching sideband is conservatively plugin-origin and refused.
- `plugin::invocation_output` applies the same algorithm to every ordinary hook argument
  before selecting the mutable output, preserving todo 151's all-or-nothing choke point.
  The auth loader applies it before `plugin_provider` and provider assignment, preserving
  todo 147's no-loss write-back rule.
