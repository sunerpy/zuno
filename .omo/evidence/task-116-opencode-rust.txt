THE DEFECT AS IT SHIPPED
========================
`export` was registered, appeared in `--help`, was recorded `Implemented` in
`crates/oc-cli/src/disposition.rs:77`, documented `implemented` in
`docs/compatibility-matrix.md:89`, and todo 56 — which owned it — was checked
`- [x]`. Every invocation printed a missing-handler message and exited 1.

Three mechanisms asserted it was fine. All three described *intent*. None ran the
handler. The disposition table and the generated matrix could never disagree,
because the matrix is generated FROM the table.

The routing cause was a fall-through: `crates/oc-cli/src/cmd/mod.rs` probed
`DispatchArguments` with a chain of `if let` and sent anything it did not
recognise to `PendingCommandDispatcher`. `Export` was never in the chain.

WHAT THE DIFFERENTIAL FOUND THAT A SHAPE ASSERTION WOULD NOT
============================================================
The first run of the oracle differential FAILED on numbers, not on structure:

  Rust:   "tokens": { "input": 1024.0, "output": 256.0, ... }, "cost": 0.0
  Oracle: "tokens": { "input": 1024,   "output": 256,   ... }, "cost": 0

JavaScript has one numeric type, so a blob holding `0.0` parses to `0` and
`JSON.stringify` writes `0`; `serde_json` preserves `0.0`. This is not a fixture
artefact — this port's own turn writer stores `"cost": 0.0` into the message blob
(`crates/oc-engine/src/loop.rs:1466`) where upstream stores `0`. Without a
normalization pass, `export` prints different bytes than the released binary
prints FROM THE SAME ROW, and a user comparing, hashing or diffing two backups
sees two different documents.

`crates/oc-db/src/session_list.rs` already had this rule for the one `cost`
column it serialises itself (`serialize_cost`, with a comment recording that it
was the only textual difference the listing differential found). The export needs
it for the whole tree, because the two `data` blobs pass through untyped.
`session_export::normalize_numbers` does that, guarded so a float outside `i64`
is left alone rather than truncated.

A test asserting "the payload has an info and a messages array" would have
passed with `1024.0` in it.

  crates/oc-cli/tests/surface.rs — four tests
    surface_no_implemented_disposition_routes_to_the_pending_handler
        For every `Disposition::Implemented` row, parses a representative argv,
        resolves the DispatchRequest, asserts `!is_pending()`, and asserts the
        command is not also in PENDING_COMMANDS.
    surface_every_implemented_command_actually_has_a_handler
        Both directions between the disposition table and IMPLEMENTED_PROBES, plus

    surface_the_pending_command_roster_is_complete_and_accurate
        Every PENDING_COMMANDS entry really is pending, carries a reason, and is

    surface_export_no_longer_reports_a_pending_handler

SIBLING AUDIT — every command whose handler returns the pending error
=====================================================================
`disposition.rs` cited "pending todo 56" at lines 48, 66 and 72 (agent, db,
debug). Those three reasons were STALE PROSE, not stubs: all three have had real
handlers since todo 56 landed. They are not liars about behaviour. Verified by
probe: agent/db/debug all resolve to their own handlers, `is_pending()` false.

Commands whose handler actually returned the pending error, before this change:

  command      disposition row        matrix said     liar?
  ---------    -------------------    ------------    -----------------------------
  export       Implemented            implemented     YES — fixed by implementing
  import       Implemented            implemented     YES — fixed by implementing
  completion   (no row at all)        (not listed)    NO — see below

`completion` is the only remaining stub. It is NOT a disposition liar: upstream
registers it through yargs's `.completion()` builtin rather than as a `*Command`
symbol, so it is absent from the symbol-keyed fixture
(`crates/oc-cli/tests/fixtures/upstream-commands-1.18.13.txt`, 23 symbols) and
therefore has no disposition row and no matrix entry. Nothing ever claimed it was
implemented. What it DID do was print "pending todo 56" — a closed build task —
so its message is now the recorded reason from PENDING_COMMANDS, and the pending
set is enumerable and test-closed in both directions.

Why `completion` was not implemented here: upstream's output is a yargs shell
function that shells back into `opencode --get-yargs-completions`, a protocol this
port does not implement. Reproducing it means either that protocol or a new
`clap_complete` dependency. Both are larger than this commit and neither is what
todo 116 asked for. The honest state is recorded rather than papered over.

Noted for todo 119, NOT changed here: the disposition table's key is the upstream
`*Command` symbol, so any command upstream registers by another route
(`.completion()` today) is structurally outside the table's coverage and outside
the "of upstream's 23 commands" counts the matrix asserts. Changing the fixture's
key would move those counts and the release-surface assertions; roster
reconciliation is todo 119's.
