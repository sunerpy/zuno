# Todo 131 evidence — HTTP-driven turn readback

Date: 2026-08-10
Baseline HEAD: `976516eca00e04d0ef0c1ecbde867f00db7e867e`

## Reproduction before the fix

The real entry point was started on isolated loopback ports:

```text
target/debug/opencode-rust serve --hostname 127.0.0.1 --port 41932
```

A local OpenAI-compatible fixture returned `HTTP_ASSISTANT_OK`. For session
`ses_fdadc9f40c9a4c57b9cc68b3935d90c3`, `POST /prompt` returned 200 and
`POST /wait` returned 204, while the client-visible read paths stayed empty:

```text
pre-opened session SSE: curl exit 28, 0 bytes
pre-opened global SSE:  curl exit 28, 89 bytes; only server.connected
GET /message:             {"data":[],"cursor":{}}
GET /history:             {"data":[],"hasMore":false}
```

The same database contained canonical user and assistant `message` rows, and a
canonical `part` row whose text was `HTTP_ASSISTANT_OK`. The provider captured
one real request. This proved that the production turn executed, but its engine
events were not connected to the HTTP `EventService` and `/message` was reading
only `session_message`, not the canonical `message`/`part` conversation.

An untouched empty session returned exactly:

```json
{"data":[],"cursor":{}}
{"data":[],"hasMore":false}
```

Both fixture and product processes were stopped by exact PID; ports 41931 and
41932 were confirmed closed.

## Implementation

- `EventService::forward_engine_events` projects each production `TurnEvent`
  into the durable HTTP event stream while retaining the existing in-process
  fanout. Durable persistence happens before SSE broadcast.
- The HTTP prompt path starts that forwarding bridge for the real production
  turn. A failed turn publishes `session.error` instead of ending in silence.
- `/message` performs one bounded merge of canonical `message`/`part` rows and
  `session_message` control rows. Canonical records win duplicate IDs, and
  `MessageStore::messages_by_id` hydrates canonical messages in a batch, so
  existing agent/model control-message behavior remains available.
- `/history` and both SSE routes consume the same durable event projection;
  there is no second event-read implementation.

## Client-boundary regression tests

The following tests exercise the HTTP surface rather than internal stores:

- `http_client_reads_one_prompt_answer_from_message_history_and_preopened_session_sse`
- `global_http_event_stream_carries_the_http_driven_turn_after_server_connected`
- `api_empty_session_message_and_history_stay_empty`
- Existing API assertions now also cover canonical conversation records and
  agent/model control records coexisting in the bounded `/message` response.

Before implementation, the pre-opened session SSE regression failed with:

```text
SSE stream must produce a data frame inside its budget: Elapsed(())
```

After the implementation was green, a reversible mutation disconnected the
durable bridge. The same session-SSE test failed again for the missing frame.
The mutation was immediately restored and the target tests passed. This proves
the regression is sensitive to the production bridge rather than merely to
database writes.

## Real serve verification after the fix

The repaired binary was started through the same real entry point on port 42132
with the fixture on port 42131. A pre-opened session stream and a pre-opened
global stream observed one HTTP-driven turn:

```text
session SSE: turn.started ... provider{text.delta:HTTP_ASSISTANT_OK} ... turn.completed
global SSE:  server.connected ... provider{text.delta:HTTP_ASSISTANT_OK} ... turn.completed
/message:    assistant text part HTTP_ASSISTANT_OK plus the user prompt
/history:    durable provider event with HTTP_ASSISTANT_OK
/wait:       HTTP 204
```

The global stream retained `server.connected` as its first frame. The session
and global streams received 2,585 and 2,674 bytes respectively before their
bounded `curl --max-time 8` calls exited 28, as expected for live SSE streams.
An empty session still returned the two exact empty payloads shown above, so no
synthetic rows were introduced. Provider PID 1340379 and server PID 1340380
were stopped, and ports 42131/42132 were confirmed closed.
