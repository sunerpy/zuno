STEP 2 — THE TEST, AND WHY IT PINS CONTENT RATHER THAN PRESENCE
--------------------------------------------------------------------------------
Added to crates/oc-cli/tests/tool_turn.rs:

  production_js_malformed_model_diagnostic_names_the_plugin_model_and_decode_reason

Shape (production boundary, matching todo 167's two tests rather than unit-testing
an emission helper):
  1. Writes the SAME `SDK_MODEL_PROVIDER_PLUGIN` .mjs fixture todo 167 built, whose
     model map is one decodable `ModelV2` plus `malformed: {providerID: "github-copilot"}`.
  2. Launches the real `opencode-rust` binary through
     `run_sdk_model_provider_prompt(..., print_debug_logs = true)`, which now prefixes
     `--print-logs --log-level DEBUG`. That is the existing idiom at
     tool_turn.rs:592-628, and it is required: `oc-observability` writes the rolling
     file always but attaches the stderr layer only under `--print-logs`, and the
     DEBUG default directive only under `--log-level DEBUG`.
  3. Asserts the run SUCCEEDED, then that the valid sibling still dispatched:
     2 captured requests, last on `/v1/chat/completions`, `model == "gpt-5"`.
     This is the isolation restatement — it fails if a future change "reports" the
     malformed model by discarding the provider or the run.
  4. Finds the ONE stderr line containing the message, then asserts three facts
     against THAT LINE:
        the plugin      -> format!("file:{}", plugin.display())
        the model id    -> "malformed"
        the decode reason -> "missing field `id`"

Why this pins content, not presence. Three independent `stderr.contains(..)` calls
would be satisfiable by three unrelated lines, and merely finding the line would
pass with every field empty. Locating the line first and then asserting its fields
means a diagnostic that fires with a blank plugin, blank model, or blank error
fails here. Mutations 2-4 below demonstrate exactly that, each on its own leg.

The two expected literals are derived, not guessed:
  - `missing field \`id\`` — `plugin_model_value` (projection.rs:294-302) renames the
    fixture sibling's only field `providerID` to `provider_id`, so serde then fails
    on `ResolvedModel`'s first missing required field, `id` (resolved.rs:49-51).
  - the plugin — `JsHost::plugin()` reports the config SPEC, so the emitted line is
    `plugin=file:/tmp/oc-testkit-XXXX/project/sdk-model-provider.mjs`. The test builds
    that from the fixture path (the same idiom as tool_turn.rs:1327's
    `broken_config.join("plugin").display()`), rather than matching a stem that could
    coincide with unrelated text. An earlier draft asserted the stem
    `"sdk-model-provider"`; it was strengthened to the exact spec after mutation 2
    printed the real line.

The one production-source change is NONE: bridge.rs is byte-identical to `main`
(md5 0a23d5e24261109624d553e789d60b16 verified after every mutation). Only
crates/oc-cli/tests/tool_turn.rs changed: the runner gained a `print_debug_logs`
parameter (existing call site passes `false`, so the two todo-167 tests keep their
exact previous command line) and the new test was added.
