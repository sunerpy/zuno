2. Why each production crate changed:

   - `oc-cli`: production integration root; dispatches hidden guard invocations
     before Clap and activates the current executable for later child launches.
     The standalone G6 fixture activates itself, so this change is production
     integration, not required to make the fixture binary work.
   - `oc-lsp`: routes every language-server process through containment; this is
     directly exercised by the two-session LSP leg of G6.
   - `oc-mcp`: routes every local stdio MCP server through containment; this is
     directly exercised by the two-session MCP leg.
   - `oc-pty`: routes every PTY shell/command through containment; this is
     directly exercised by the two-session PTY leg.
   - `oc-plugin`: the JSON-RPC process path is directly exercised by G6. The
     JavaScript runtime host was also routed through the same guard for uniform
     coverage of the crate's second persistent external-host implementation;
     that JavaScript path is not exercised by this G6 fixture.

   `oc-acp` is separate G5 scope: its ninth queue was observed by the
   source-derived registry and changed from unbounded to bounded lossless block.

3. Guard activation and ordinary-launch behavior:

   `guarded_argv` is deliberately an identity operation before activation, so a
   library/test process that does not install a guard still launches the host
   directly. Production `opencode-rust` does not silently fall back after it
   chooses containment: an ordinary invocation first bypasses hidden guard
   dispatch, resolves `current_exe`, activates that executable, and then enters
   the existing CLI. If locating or activating the guard fails, startup prints
   the error and exits failure; if a hidden guard cannot arm or spawn its next
   stage, it exits failure and does not retry the host unguarded. This is
   fail-closed containment, not best-effort fallback. Linux uses PDEATHSIG plus
   a process group; other Unix targets use parent polling/signals plus a process
   group; Windows uses a Job Object. The runtime G6 proof in this evidence is
   Linux-only.

SOURCE-DERIVED G5 INVENTORY
===========================
`source_channel_inventory_matches_the_declared_registry` walks production Rust
sources, strips cfg(test) modules, recognizes bounded and unbounded constructors
across line breaks, and compares the exact construction set with `CHANNELS`.
Every non-excluded entry declares a capacity, overflow policy, source evidence,
and a dedicated test. The policies exercised are lossless block, broadcast lag,
latest value, coalesce-full, refuse-newest, subscriber lag, and closed-drop.

ACP's former unbounded outbound frame path is now a Tokio mpsc queue with
`OUTBOUND_FRAME_CHANNEL_CAPACITY = 64`; producers await send, so saturation is
lossless bounded blocking rather than growth. The two exclusions are one-result
plugin completion channels whose producers send exactly once and cannot
accumulate an open-ended backlog.

G6 CONTAINMENT
==============
`oc-process` supplies one guard protocol used by LSP, MCP, PTY, JSON-RPC plugin,
and JavaScript plugin launches. On Linux the monitor owns a process group and
uses `PR_SET_PDEATHSIG`; it kills the complete host process group both when the
caller disappears and when the direct host exits before descendants. The real
fixture starts two public-API sessions for every host kind and gives every host
a grandchild, so PID enumeration covers the complete transitive tree rather
than only direct children. Windows uses pinned `process-wrap = 9.1.0` Job
Objects; Linux is the platform exercised by these G6 tests.
