ACCEPTANCE CRITERION 3 — subpath actually filters
--------------------------------------------------------------------------------
`the_project_scope_with_a_subpath_actually_filters`:
  project prj_a holds ses_a_root (path ""), ses_a_pkg ("pkg"),
  ses_a_pkg_core ("pkg/core"), ses_a_pkgx ("pkgx").
  list(project=prj_a)                  -> 4 rows
  list(project=prj_a, subpath="pkg")   -> ["ses_a_pkg", "ses_a_pkg_core"]
  ses_a_pkgx excluded (shares a prefix, is not beneath it)
  ses_a_root excluded (empty path is not beneath "pkg")

`a_subpath_containing_a_like_wildcard_is_not_treated_as_a_pattern`:
  subpath "a_b" returns only the session under a_b/, not the one under axb/.
  Upstream's `path LIKE 'a_b/%'` would match both. Divergence, deliberate.

`a_subpath_never_crosses_a_project_boundary`: two projects sharing one worktree,
one session each under pkg/; subpath "pkg" on prj_a returns only prj_a's.

`the_real_binary_reads_rust_written_sessions_in_the_same_order`
  Rust list(global) default order == oracle's
  `ORDER BY time_updated DESC, id DESC` on the same rows, including a
  deliberate time_updated tie (ses_a_pkg / ses_a_pkg_core both at 400) that only
  the id tie-break can resolve. Also checks the opt-in created sort against
  `ORDER BY time_created DESC, id DESC`.

  Rust list(project, subpath="pkg") == oracle's
  `WHERE project_id = ? AND (path = 'pkg' OR path LIKE 'pkg/%')`,
  and the unfiltered project listing is strictly larger (4 vs 2) — which is what
  upstream's v2 `list` returns today for the same request.

  3-level tree on a real file, `remove` + `wal_checkpoint(TRUNCATE)`, then the
  real binary reports 0 rows in session, message, part, event, event_sequence.

ENVIRONMENT NOTE (not a source defect)
--------------------------------------------------------------------------------
`cargo test --workspace` in this worktree failed four consecutive times with
  error[E0432]: unresolved import `oc_db::session`  (in my own tests/session.rs)
while `cargo test -p oc-db` compiling the identical target passed every time.
`cargo test -v` showed a single `--extern oc_db=.../liboc_db-d62e9bf3e72b3176.rlib`,
1,100,492 bytes — about half the size of the oc-db rlib this worktree produces —
and an earlier doctest run failed with "extern location for oc_db does not
exist" naming that same hash. `ps` showed three sibling `cargo test --workspace`
processes on the shared CARGO_TARGET_DIR, and target/debug/deps held several
zero-byte liboc_db-*.rmeta files mid-write. Todo 22 is in the same crate.
Diagnosis: cross-worktree artifact contention on the shared target directory,
same class as the documented `cargo clean -p <crate>` hazard.
Every workspace-wide number above was therefore measured with
CARGO_TARGET_DIR=/tmp/oc-t21/target (isolated, on /dev/root which had 205G free);
/config was at 84%. `cargo clean -p oc-db` also cleared it once, transiently.
