7. Locked-list rebuild happens AT MOST ONCE
================================================================================
catalog_late_connection_rebuilds_the_locked_tool_list_exactly_once
  request 1 (0 servers, Pending)     -> [],                            rebuilt=false, count=0
  docs connects; request 2 (Pending) -> [],                            rebuilt=false, count=0
  wiki connects -> Ready; request 3  -> [docs_search, wiki_search],    rebuilt=true,  count=1
  a THIRD server connects; request 4 -> [docs_search, wiki_search],    rebuilt=false, count=1
  five further requests              -> unchanged,                     rebuilt=false, count=1

catalog_settled_first_request_never_spends_the_rebuild
  discovery already Ready on request 1 -> a later connection never rebuilds; count stays 0.

The once-only property belongs to todo 31's LockedTools. Catalog::tools_for_request
feeds it the whole id list plus discovery_status() and NEVER calls reset() — a reset
would re-arm the allowance (mutation 2).

discovery_status() gating (catalog_discovery_stays_pending_until_every_expected_server_reports):
  Pending until every expected server has reported success OR failure;
  a failure counts as a report; zero configured servers is immediately Ready.

10. WHAT THE PLAN GOT WRONG / NEEDED INTERPRETATION
================================================================================
a) "all three mapped onto the `read` permission key" — already done. oc-permission's
   READ_TOOLS (visibility.rs:30-34) contains exactly those three literals and
   permission_key collapses them. Nothing to add; I assert against it instead of
   copying it. No oc-permission edit was needed or made.

b) "expose MCP prompts to the command resolver (wave 3 precedence)" — the seam
   existed and is richer than the plan implies: oc_catalog::command::Sources has
   with_mcp_prompts(&[McpPrompt]) at level 3, plus a two-phase Resolution::PendingMcp
   for the deferred prompts/get. What did NOT exist was any way to obtain prompts:
   neither StdioClient nor RemoteClient had prompts/list. I added it in oc-mcp.

c) Same gap for resources: the crate's own lib.rs doc line said "tools, resources,
   prompts" but only tools existed. resources/list, resources/templates/list,
   resources/read and prompts/list are new here; without them the three resource
   tools would have had no transport.

d) The plan's reference `packages/opencode/src/session/tools.ts:388-492` describes
   "dynamic registration and execution" as splitting the namespaced id back into
   server+tool at call time. It does not. The oracle captures the original
   definition and client in a closure (mcp/catalog.ts:42-67); only code-mode
   approximates a split, and only for display (tool/code-mode.ts:39-55). I follow
   the oracle, not the plan's prose — splitting would be unsound because the
   sanitizer is not injective.

e) The three resource tools are gated on a connected server declaring a `resources`
   capability (session/tools.ts:155-157). The plan does not mention this gate; without
   it a config with no resource-capable server advertises three tools that can only fail.
