缺陷 A 根因（已复现，非 Zuno 缺陷）
=================================
`~/.cargo/bin/rust-analyzer` 是 rustup 的 proxy 符号链接，只要装了 rustup 就存在，
与 `rust-analyzer` component 是否安装无关。CI 的 dtolnay/rust-toolchain 只装了
`rustfmt,clippy`（.github/workflows/ci.yml:66-69），所以 proxy 存在但 component 没有。

本机复现（剥掉 mise fallback 后与 CI 完全一致）：
    $ env -i HOME=/config PATH=/config/.cargo/bin:/usr/bin:/bin RUSTUP_TOOLCHAIN=1.90.0 \
        /config/.cargo/bin/rust-analyzer --version
    error: Unknown binary 'rust-analyzer' in official toolchain '1.90.0-x86_64-unknown-linux-gnu'.
    exit=1

本机默认 PATH 下反而看不出问题（这就是「本机绿 / CI 红」的来源）：
    info: `rust-analyzer` is unavailable for the active toolchain
    info: falling back to "/config/.local/share/mise/shims/rust-analyzer"
    rust-analyzer 1.96.0 (ac68faa 2026-05-25)   exit=0

链路：proxy 秒退 → ManagerError::Initialize{ClientError::Closed}
     → supervisor 用尽 RestartPolicy::default() 的 6 次 launch
       （退避 100+200+400+800+1600ms ≈ 3.1s）→ publish_stopped
     → wait_for_client 观察到 Stopped → ManagerError::Unavailable
CI 时间戳佐证：19:55:05.5 套件开始 → 19:55:09.26 报错 = 3.76s，
与退避总和吻合，**不是** CLIENT_READY_TIMEOUT(50s) 触发。

因此这不是 Zuno LSP 客户端可修的 readiness/timeout 问题：进程根本不是语言服务器。
修 readiness 的唯一替代方案是给 CI 装 rust-analyzer component，那要改
.github/workflows/**（本任务禁止）。故按要求把第三态实现为「带原因的跳过」。

oc-lsp readiness 语义（探测所得，支撑上述判断）
- Unavailable{server_id} 仅 3 个构造点，全在 manager.rs:696-721 wait_for_client：
  supervisor 已 Stopped / watch channel 关闭 / CLIENT_READY_TIMEOUT(50s) 耗尽。
- 真实根因（Registry::NotInstalled、Spawn、MissingPipe、
  Initialize{Framing|Protocol|Closed|Timeout}）被 supervisor tracing::warn! 后折叠，
  公开 API 只剩 Unavailable。
- 超时常量：INITIALIZE_TIMEOUT=45s、REQUEST_TIMEOUT=10s、DIAGNOSTICS_TIMEOUT=20s、
  CLIENT_READY_TIMEOUT=50s。
- $/progress（含 rustAnalyzer/Indexing）被 dispatch_message 静默忽略，不参与 readiness。
- Manager::diagnostics 对 diagnostics 超时不报错，回落缓存快照 → 表现为「成功但空」。


缺陷 A 修复：三态守卫（crates/oc-lsp/tests/live_rust_analyzer.rs）
================================================================

TypeScript 侧覆盖评估（如实说明，未补写）
=======================================
删除的用例除 oracle 对比外，唯一独立断言是 `!actual.is_empty()`
（Zuno 能从真实 typescript-language-server 拿到诊断）。
改后仍存在的 TypeScript 覆盖：
  - config/registry 层：oc-lsp/src/registry.rs 单测断言 typescript 内建 spec 的
    command(["typescript-language-server","--stdio"])、extensions、env、initialization
    与用户覆盖（registry.rs:878-901）。
  - 协议层：oc-lsp/src/{manager,client}.rs 的 Python stub server 单测（hermetic，
    server 无关）覆盖 initialize/publishDiagnostics/重启/降级。
真正失去的：真实 typescript-language-server 的端到端 live 覆盖，现在只剩
  oc-testkit/tests/soak.rs 的 G3/G4，而它是 #[ignore]（两小时），CI 不跑。
选择：**不补写**新的 oracle-free TypeScript live 测试。理由是它不 hermetic ——
必须 PATH 上有 typescript-language-server，CI 上没有，落地即又一个「看着通过其实
什么都没测」的 hollow gate，正是本仓库反复出现的缺陷类。这一点如实记入 issues.md，
未静默降低覆盖。
