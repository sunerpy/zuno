5. THE CONTEXT-WINDOW SOURCE — found, not invented
--------------------------------------------------------------------------------
Field:  oc_llm::catalog::resolved::ModelLimit { context: f64, input: Option<f64>,
        output: f64 }        (crates/oc-llm/src/catalog/resolved.rs:164-172)
Origin: models.dev `limit.context` / `limit.output`
        (crates/oc-llm/src/catalog/models_dev.rs:118-121), carried through
        merge.rs:204 and merge.rs:486-490 so a config override wins.

Read once, in TurnPlan::resolve:
    let window = TokenWindow {
        context:    token_count(catalog_model.limit.context),
        max_output: token_count(catalog_model.limit.output),
    };

They are f64 because models.dev publishes JSON numbers. `token_count` maps a
non-finite, negative or zero value to 0, and 0 already means "no threshold
compaction" to CompactionPolicy — pinned by
  turn_tests::a_catalog_limit_that_is_absent_or_negative_reads_as_no_window

Upstream reads exactly the same two fields for the same decision
(packages/opencode/src/session/overflow.ts:10-19: `input.model.limit.context`,
`limit.input`, `maxOutputTokens`), so no constant was invented and none is
needed. I did NOT use `limit.input`: TokenWindow has no field for it, and adding
one would change todo 35's tested type. Recorded as a known gap — a model that
declares a smaller input ceiling than its context window will compact slightly
later than upstream would.

7. HOW THE APPEND-ONLY CACHE VIOLATION WAS AVOIDED
--------------------------------------------------------------------------------
Todo 105's first attempt died on
  append-only cache violation on turn 2: stable history message 1 changed
  (crates/oc-llm/src/cache.rs:153)
and this task adds a request to the FRONT of every turn — the same shape.

It does not fire, and the reason is structural rather than lucky:

  * run_turn creates its PromptCache/CacheTracker INSIDE the call
    (loop.rs:561 `let mut prompt_cache: Option<PromptCache<..>> = None`).
    Every prelude write lands before that call, so the tracker's first
    observation is already the post-prelude, post-compaction prefix. There is no
    prefix for it to compare against and nothing to reset.
  * The prelude's own two requests never touch that tracker at all. They are
    built by prelude::collect_text as bare CompletionRequests with tools: [].
    Compaction has its own CacheTracker + LockedTools, created and dropped
    inside compact_if_overflowing.
  * Compaction never mutates a stored message in place. It APPENDS a marker
    user message, an assistant summary message and the summary text; honouring
    it is loop::retained_history dropping a PREFIX of stored history. The
    messages the tracker sees are therefore still append-only relative to each
    other within the turn.
  * The prompt is still stamped with oc_db::message::created_after (todo 105's
    clamp), which the prelude did not disturb.

Verified, not assumed: tool_turn.rs and tui_turn.rs both pass, and turn 2 of the
tool loop (the continuation after the tool result) is exactly the step that
failed before.
