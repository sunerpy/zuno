CONCURRENT-ACQUIRE POLICY: REFUSAL
A second acquire against a live lease returns TerminalLeaseError::Busy naming the
holder. Not queueing (a queued device-code prompt arrives with no context on a
terminal the user left, and a never-releasing host would turn every later acquire
back into a hang — the exact defect the lease removes). Not preemption (revoking
mid-prompt yanks the terminal from under half-typed input). The only involuntary
transition is the deadline.

FORCE-RECLAIM OWNER: TWO PATHS, ONE SETTLE-ONCE FLAG
1. A watchdog tokio task spawned per grant, cancelled by the guard's oneshot
   sender being dropped (so a panic unwind also cancels it).
2. A sweep at the top of acquire, plus the public reclaim_if_expired().
Both AtomicBool::swap the same flag, so reclaim_terminal runs exactly once per
grant. Path 2 exists because path 1 needs a live Tokio runtime; acquire uses
Handle::try_current and degrades to sweep-only rather than panicking.

FORCE-RECLAIM DIAGNOSTIC (verbatim, ForcedReclaim::Display)
plugin `kiro` held the terminal for `device-code prompt` past its 0 ms deadline and did not release it; the terminal was reclaimed by force
