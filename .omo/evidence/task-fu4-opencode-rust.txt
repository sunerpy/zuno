Mechanical binding set determined before code:
- Requests: POST `/api/session` -> `SessionCreate`; POST `/api/session/prune` -> `SessionPruneMutation`.
- Responses: GET `/api/session` -> `SessionListResponse`; POST `/api/session` and GET `/api/session/{sessionID}` -> new component name `SessionResponse`, generated from existing `Data<SessionInfo>` derives without changing `Session`; GET `/api/session/active` -> `SessionActiveResponse`.
- Existing component shapes and `operationId` remain untouched. Publishing a local `Agent` schema is explicitly outside this mechanical set: `AgentInfo` plus its envelope/nested catalog types derive only `Serialize`, so doing it now would be new schema authorship. It is frozen as remaining type work rather than hand-authored to make the count rise.

TDD RED — LOAD-BEARING RESPONSE VALIDATION
- Added `api_session_response_validates_against_its_published_openapi_binding` in `crates/oc-server/tests/api.rs`.
- Shape: the test inserts a real session, fetches `/doc` through the assembled router, derives the GET session response component from the operation's published `$ref`, compiles that exact component with `jsonschema`, fetches the real `/api/session/ses_schema` response, and validates the returned JSON against the published component. No required field list is hard-coded.
- Dependency decision: `jsonschema = =0.37.1` was added as an exact, default-feature-free dev dependency of `oc-server`. The same exact crate/version is already used by first-party `oc-engine` and present in the lockfile. Rejected alternative: a local partial validator for `required`/`type`/`$ref`, because it would claim schema validation while silently ignoring the rest of JSON Schema.
- Red command: `CARGO_TARGET_DIR=/tmp/opencode/fu4 cargo test -p oc-server --test api api_session_response_validates_against_its_published_openapi_binding --offline`.
- Observed behavioural failure (the test compiled and ran): panic `GET /api/session/{sessionID} publishes a JSON response schema reference`; result `0 passed; 1 failed`. This is the intended pre-implementation failure, not a compile error.

IMPLEMENTATION
- Added request bindings: POST `/api/session` -> `SessionCreate`; POST `/api/session/prune` -> `SessionPruneMutation`.
- Added response bindings: GET `/api/session` -> `SessionListResponse`; POST `/api/session` and GET `/api/session/{sessionID}` -> `SessionResponse`; GET `/api/session/active` -> `SessionActiveResponse`.
- `SessionResponse` is generated mechanically from the existing `Data<SessionInfo>` and nested `JsonSchema` derives. Existing component shapes and `operationId` values were preserved.
- The 60-operation surface is partitioned by an executable guard into 5 operations with bindings, 8 genuinely bodyless operations, and 48 operations with incomplete body coverage. POST `/api/session/prune` is both bound on its request side and frozen for its still-untyped response, so these categories intentionally overlap at the operation level only where one body side is complete and the other is not.
- `openapi_body_schema_gaps()` exposes the single 48-entry `(path, method, reason)` inventory. `oc-testkit::compat_report::known_gaps` consumes it directly as `openapi-body-schema-bindings`, and `docs/compatibility-matrix.md` is generated from that same value. No gap reason is duplicated in report or documentation code.
- `api_openapi_binds_every_body_with_an_existing_rust_schema` pins all six request/response `$ref` bindings. `every_operation_is_bound_bodyless_or_a_reasoned_frozen_gap` rejects duplicates, empty reasons, unregistered inventory entries, and any operation outside the three-state accounting.
