0. RESULT
---------
Chose to SERVE both upstream SSE operations rather than declare a divergence:

  GET /api/event
  GET /api/session/{sessionID}/event

The event service and durable store already contained the required capability.
Leaving an asynchronous client primitive absent, or declaring a divergence merely
because its upstream path had not been wired, would have preserved a user-visible
gap without a technical reason. The implementation therefore shares the existing
EventService with ApiState and exposes the upstream routes with tested behaviour.

Measured operation count from the committed 1.18.12 OpenAPI capture: 58. The
served OpenAPI now contains all 58, plus the two already-declared C8 maintenance
operations. Path presence is only an inventory assertion; it is not the parity
claim.


1. SSE BEHAVIOUR
----------------
GET /api/event:

  * returns an SSE response and immediately emits `server.connected` with `{}`;
  * then emits events published through the shared EventService;
  * a session created through POST /api/session is persisted and observed on the
    same global stream as `session.created`, including the session id and info.

GET /api/session/{sessionID}/event:

  * replays durable events for only the requested aggregate;
  * `?after=<sequence>` resumes strictly after that durable sequence;
  * returns the upstream durable body shape (`aggregateID`, `seq`, `version`);
  * omits the legacy sequence-zero `session.created` row from the public v2
    session-event stream and continues with subsequent live events.

Named behavioural tests in `crates/oc-server/tests/events.rs`:

  upstream_global_event_stream_emits_connected_then_published_events
  creating_a_session_is_observable_on_the_upstream_global_stream
  upstream_session_event_stream_replays_after_sequence_with_durable_shape
  upstream_session_event_stream_omits_legacy_creation_rows

The API and CLI composition roots now pass the same EventService into ApiState,
so session mutation and event subscription do not accidentally use disconnected
buses.


2. BEHAVIOUR MATRIX SHAPE
-------------------------
`api_behaviour_matrix()` creates exactly one row for each of the 58 captured
upstream operations. Every row has three independently visible dimensions:

  status | normalized body | observable side effect

The live differential starts isolated released and Rust servers and invokes every
row against both. Non-SSE side effects are measured as the before/after delta of
the public session and PTY collections. SSE side effects record the event type and,
for durable session events, the sequence. The only body normalization removes
independently generated identities: the SSE envelope id, timestamp, and messageID.
Event type, aggregate id, sequence, version, stable data, status and side-effect
semantics remain compared.

Five deterministic operations compare all three dimensions exactly (15 compared
dimensions):

  GET /api/health
  GET /api/session
  GET /api/session/active
  GET /api/event
  GET /api/session/{sessionID}/event

The remaining 53 rows are still invoked against both processes and capture all
three observations, but each dimension carries an explicit fixture exemption
(159 exempt dimensions). Of those rows, 45 are honest local backend gaps: the Rust
operation returns operation-specific `503 backend_unavailable`, has no side effect,
and is never counted as parity. Eight have a local backend but cannot be seeded
identically across the two isolated processes with the current public fixture:

  GET /api/location
  POST /api/session
  GET /api/session/{sessionID}
  GET /api/pty
  POST /api/pty
  GET /api/pty/{ptyID}
  PUT /api/pty/{ptyID}
  DELETE /api/pty/{ptyID}

4. A 501 CANNOT PASS
--------------------
There are two independent guards:

  * `compare_api_observation()` rejects status 501 before equality or any
    exemption is considered. `api_behaviour_matrix_rejects_a_501_only_operation`
    constructs equal oracle/subject 501 observations and proves the comparison
    still fails with a message naming 501.
  * Every subject operation is really invoked by
    `api_behaviour_matrix_invokes_every_subject_operation_and_rejects_501`;
    `assert_subject_operation_is_accounted()` rejects 501, requires a non-empty
    JSON body, and requires every 503 to carry `error.code=backend_unavailable`,
    produce no observable state change, and be marked exempt in all dimensions.

The generated compatibility documentation uses the same runtime probe: 501 fails,
503 is rendered as `explicit gap (503 backend unavailable)`, and only a backed
non-gap response is rendered as implemented.
