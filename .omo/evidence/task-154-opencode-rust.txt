Task 154 — bound compatible-provider streaming idle reads
Closes F3-W9-D2.

DEFECT REPRODUCTION
--------------------------------------------------------------------------------
A purpose-built chunked HTTP server sent `PARTIAL_` and then either closed or held
the socket open:

  real FIN:   EXIT=1 elapsed_ms=1103; partial text and the connection-reset cause
              were printed.
  held open:  EXIT=124 elapsed_ms=4003 under an external timeout; the process did
              not terminate by itself. This build flushed `PARTIAL_` when killed,
              unlike F3's zero-byte capture, but the idle read remained unbounded.

IMPLEMENTATION
--------------------------------------------------------------------------------
`ReqwestTransport` now resolves a 120-second response idle timeout through
`StreamIdleTimeout::from_config`, preserving the existing
`OPENCODE_STREAM_IDLE_TIMEOUT_SECS` override. The timeout wraps each individual
`body.next()` operation, not the whole request, so every successful response chunk
starts a fresh allowance. A timeout becomes a transient `ResponseIdleTimeout`
which names the provider, duration, and configuration override. Chunks received
before the timeout remain successful stream items and are not discarded.

The 120-second default accommodates the established >90-second reasoning-gap
policy while terminating before F3's 200-second liveness bound. No dependencies
were added. Dedicated OpenAI and Anthropic transports were audited and already
bound every `response.chunk()` read with the shared idle-timeout policy.

FOLLOW-UP: PRODUCTION DEFAULT AND OVERRIDE GUARDS
--------------------------------------------------------------------------------
Review found that both original socket tests supplied a short timeout explicitly,
so they proved the per-read mechanism but not the production value or its wiring.
Before this follow-up, changing `DEFAULT_RESPONSE_IDLE_TIMEOUT` from 120 seconds to
86400 seconds left the entire provider-compatible suite green.

`production_transport_installs_a_sane_default_idle_timeout` now checks both sides
of that seam: the configured default accommodates the established 90-second
reasoning gap but remains below F3's 200-second liveness probe, and
`ReqwestTransport::new` installs the timeout resolved from that default.

Exact requested mutation:

  DEFAULT_RESPONSE_IDLE_TIMEOUT = Duration::from_secs(86400)
  cargo test -p oc-provider-compatible --offline

Result: the suite failed specifically by name at
`transport::tests::production_transport_installs_a_sane_default_idle_timeout`
with `the production default must terminate before the liveness probe`; 61 other
library tests passed. The constant was restored to 120 seconds.

Environment audit: `StreamIdleTimeout::from_config` already rejects missing, zero,
empty, and malformed `OPENCODE_STREAM_IDLE_TIMEOUT_SECS` values by retaining the
configured default; `sse_invalid_idle_timeout_environment_value_keeps_config`
covers those cases. It did accept arbitrarily large positive values, so 86400
seconds could effectively restore the hang. Compatible transports now cap every
resolved environment or programmatic override at 180 seconds, leaving 20 seconds
inside the 200-second probe for scheduling and error propagation.
`an_excessive_idle_timeout_override_cannot_restore_the_hang` proves an 86400-second
override is installed as 180 seconds instead. After restoration and the cap:

  cargo test -p oc-provider-compatible --offline
  result: 63 library + 9 cassette + 6 discipline + 12 rules + 2 doc tests passed
