HOW THE RECORDED VALUE IS BOUND TO THE BINARY (the F1/B1 fix)
------------------------------------------------------------
Before: `compat_suite.rs:68` hard-coded
        /config/.local/share/mise/installs/opencode/1.18.12/opencode
        while `compat_suite.rs:71` and `compat_report.rs:320` recorded "1.18.13".
        Nothing could fail over the gap.

After:  the *release* is declared once; the *path* is discovered.

  Oracle::discover_pinned()            src/oracle.rs — discover() (OC_TESTKIT_ORACLE, else
                                       PATH, else source tree), then check_pin() against
                                       Oracle::reported_version(), which is the trimmed
                                       first stdout line of really executing `--version`
                                       in probe_version().
  resolved_oracle()                    tests/compat_suite.rs — resolves once; absence →
                                       None (skip contract preserved); WRONG RELEASE →
                                       panic, so no report can be produced by a build
                                       other than the pin.
  report assertion                     tests/compat_suite.rs — report.oracle.version
                                       (probed) == report.oracle.pinned_source_version
                                       (claimed), whenever the oracle was available.

The assertion is NOT between two written-down constants. The right-hand side of the unit
gate is process stdout. That was the trap this task was warned about and it is avoided.

Resolved on this host:
  which("opencode") → /config/.local/share/mise/installs/opencode/1.18.15/opencode
  `--version`       → 1.18.15
(The mise shim /config/.local/share/mise/shims/opencode also reports 1.18.15; discovery
lands on the real install directly. No absolute path is written in any source file.)
