# Todo 132 evidence — HTTP permission/question broker

Date: 2026-08-10

## Implementation

- `RequestBroker` owns process-local pending permission and question requests,
  parks each production HTTP turn on a oneshot receiver, publishes asked/replied
  events through the existing `EventService`, and supports session-filtered list
  operations.
- `opencode-rust serve` injects broker-backed `PermissionAsker` and
  `QuestionAsker` collaborators only into HTTP-driven turns. Non-HTTP headless
  execution keeps `HeadlessApproval`, and the TUI path is unchanged.
- Reply/reject handlers validate the branded request ID and reply body before
  checking request ownership, matching upstream's schema middleware. A malformed,
  oversized, incomplete, or disconnected reply still claims a matching owned
  request solely for fail-closed cleanup; dropping that claim sends rejection,
  while another session's pending request is never consumed.
- The four newly backed operations were removed from `FROZEN_API_GAPS`. The
  compatibility surface is now 48 backed operations and 10 explicit gaps; the
  behavior matrix contains 93 compared and 81 exempt dimensions.

## Parity correction and mutation sensitivity

The full live matrix rejected the original claim-before-parse ordering because a
malformed permission reply produced `404` locally while upstream produced `400`.
Upstream `PermissionV2.ReplyInput` requires `requestID` and `reply`, and the HTTP
schema middleware runs before the handler's ownership lookup. Question IDs are
likewise branded with the `que` prefix. The corrected route order is therefore:
validate branded path ID, parse body where present, then check ownership. On body
failure only an owned request is claimed and dropped for fail-closed cleanup.

Changing `PermissionResolution::drop` from `ReplyKind::Reject` to
`ReplyKind::Once` made
`disconnected_permission_reply_fails_closed_without_running_the_tool` fail
because the forbidden shell side-effect file was created.
