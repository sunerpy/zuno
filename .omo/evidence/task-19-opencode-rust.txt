11. FINDING — 2 of the 4 pragmas would pass a naive readback test even if unset
--------------------------------------------------------------------------------
libsqlite3-sys build.rs passes -DSQLITE_DEFAULT_FOREIGN_KEYS=1:
126:            .flag("-DSQLITE_DEFAULT_FOREIGN_KEYS=1")
rusqlite calls sqlite3_busy_timeout(db, 5000) on every connection it opens:
118:            let r = ffi::sqlite3_busy_timeout(db, 5000);
Stock SQLite defaults foreign_keys OFF — measured on the system CLI:
  system sqlite3 3.53.4, fresh db, PRAGMA foreign_keys -> 0

Consequence: on THIS driver, foreign_keys and busy_timeout read back correct even if
the crate never issued them, so the acceptance criterion alone does not prove the
code works. Three things close that gap:
  - tests/open.rs::the_stack_below_this_crate_already_defaults_two_pragmas_to_the_
    oracle_values pins both environment defaults, so a driver bump that flips either
    one fails loudly instead of silently disabling cascades.
  - synchronous and cache_size do NOT default to the oracle values;
    wal_survives_a_close_but_the_per_connection_pragmas_do_not proves they reset on
    reopen, so this crate's pragma application is load-bearing for those two.
  - the behavioural FK proof in section 8 demonstrates enforcement rather than
    configuration, with a foreign_keys=OFF control showing the same insert accepted.
