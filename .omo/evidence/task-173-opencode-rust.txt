- Task 168's evidence establishes the shared containment condition: a callback error is non-fatal only after the plugin records a `PluginDiagnostic` and `Plugin::is_disabled()` becomes true; `HookBus` then returns `Ok(())`.
- `PluginRuntime::apply_catalog` is outside that condition. It turns `auth.loader` and `provider.models` errors directly into `Err(String)`, and the shared call is reached by `run`, `models`, and HTTP turn resolution.
- Upstream's SDK contract is `loader?: (auth: () => Promise<Auth>, provider: Provider) => Promise<Record<string, any>>` (`packages/plugin/src/index.ts:88-90`), so `null` is not a legitimate `Auth` value.
- Upstream deliberately skips the loader before constructing `getAuth` when no stored credential exists (`packages/opencode/src/provider/provider.ts:1548-1563`: `if (!stored) continue`). The Rust host must likewise not invoke the loader in the configured-but-not-logged-in state; synthesizing an `Auth` is rejected.
- `.omo/refs/` is absent from this worktree. The main checkout's `.omo/refs/` was inspected; its five reference projects do not contain the opencode plugin SDK `AuthHook` declaration. The pinned upstream source provides the authoritative signature above.

Implementation and three-surface regressions
--------------------------------------------
- `PluginRuntime::apply_catalog` now walks each owning JavaScript plugin directly so a failing retained resource callback can disable that plugin. Both `auth.loader` and `provider.models` call `JsPlugin::disable_after_callback_failure`, which records the same `PluginDiagnostic` and permanent disabled state used by ordinary `HookBus` callbacks.
- A configured provider with no stored credential skips `auth.loader`, matching upstream and preserving the SDK's `getAuth(): Promise<Auth>` contract. `StoredCredential` therefore always contains a real credential; no fake or null `Auth` crosses the plugin boundary.
- `models` prints newly recorded plugin diagnostics at default verbosity before shutdown, so successful model output does not hide the disabled plugin and its cause.
- The following real-binary regressions passed after implementation:
  - `failing_auth_loader_is_disabled_and_cli_run_completes_with_a_diagnostic`: `run` exits successfully, reaches the mock provider, and stderr names `cli-failing-auth-loader`, `auth.loader`, and `task173 CLI auth loader failure`.
  - `failing_auth_loader_is_disabled_and_models_lists_models_with_a_diagnostic`: `models test` exits successfully, prints `test/test-model`, and stderr names the plugin, hook, and cause.
  - `failing_auth_loader_is_disabled_and_http_turn_completes_with_a_diagnostic`: the HTTP turn emits no `session.error`, reaches `turn.completed`, persists the assistant response, and publishes the actionable diagnostic over SSE.
- The named not-logged-in regression `configured_provider_without_stored_auth_does_not_invoke_auth_loader` passes and proves the callback is not invoked at all without stored auth.
- `every_hook_surface_failure_boundary_is_non_fatal_by_name` covers all four requested surfaces (`run`, `models`, TUI, HTTP), all 21 authoritative hooks, and 67 applicable hook × surface entries. Ordinary callback and shutdown entries execute the real production `HookBus::dispatch` containment branch; retained `auth` and `provider` resource callbacks are covered by the production JavaScript loader tests above.
