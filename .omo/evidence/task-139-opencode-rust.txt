1. REPRODUCED GAP — THE PLUGIN LOADED, BUT ITS PROVIDER NEVER REACHED USERS
--------------------------------------------------------------------------------
Before this change, the two real binaries were run under the user's own plugin
configuration and compared through the plain `models` command (not a synthetic
catalog API and not the nonexistent `models --format json` flag):

  released 1.18.15: 10 providers
  this port:          8 providers
  missing here:       kiro-auth, opencode

`google`, contributed by `opencode-antigravity-auth`, was already present on both
sides. `--print-logs` contained no kiro mention, showing that the user-facing
models path never reached the kiro contribution rather than merely filtering an
empty result.

The new production-path regression test initially failed with exactly:

  providers={"google"}
  stdout="google/gemini-test\n"

That failure pins the original seam: loading a real plugin alone cannot satisfy
the test; its provider models must appear in the command's actual stdout.


2. ROOT CAUSES AND PRODUCTION FIX
--------------------------------------------------------------------------------
The missing contribution crossed four independent seams:

  * `models` parsed the static catalog without loading configured JS plugins or
    consuming their `ProviderHook.models` loaders.
  * the JS `config` hook was called as `(input, output)`, although the SDK mutates
    one `Config` argument; the compatibility layer then swallowed that mismatch.
  * `ProviderHook.models` received one `{provider, auth}` object instead of the
    SDK's `(provider, context)` arguments.
  * the acceptance environment's `PATH=/usr/bin:/bin` hid user-installed Bun and
    mise shims, preventing a real plugin runtime from being discovered.

The implementation now:

  * loads configured JS plugins in configuration order on the `models` path;
  * invokes their one-argument mutable `config` hooks before catalog parsing;
  * gathers provider hooks and invokes each models loader as `(provider, context)`;
  * replaces that provider's catalog models with the loader result through
    `Catalog::replace_provider_models`;
  * acquires a non-interactive terminal lease for the JS runtime lifecycle;
  * preserves `PATH` precedence while falling back to standard BUN_INSTALL,
    MISE_DATA_DIR, XDG_DATA_HOME and HOME installation locations.

No provider name is hard-coded. In particular, neither `kiro-auth` nor `google`
is inserted by Rust catalog code; both names and model sets come from the real
plugins' hooks.

--------------------------------------------------------------------------------

  opencode-antigravity-auth@1.6.0
  @sunerpy/opencode-kiro-auth@0.20.6

The test also runs with `PATH=/usr/bin:/bin`, proving runtime discovery does not

assertion prevents the antigravity path from regressing.

--------------------------------------------------------------------------------

`models` output and compared as sorted sets:

  this port after fix: 9 providers, including google and kiro-auth
  released 1.18.15:   10 providers

The remaining `opencode` difference is expected and deliberately not conflated
with this task. It is the upstream product's compiled-in hosted provider (for
models such as `opencode/big-pickle`), not output from either configured auth
plugin. This task routes real plugin contributions; it does not invent or clone
an unrelated hosted service.
