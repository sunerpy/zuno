Upstream decision evidence
--------------------------
- The installed oracle `/config/.local/share/mise/installs/opencode/1.18.18/opencode --version` reports `1.18.18`.
- Upstream source `packages/opencode/src/session/retry.ts:68-75` explicitly classifies every HTTP 5xx as retryable, even when the provider SDK does not. Its retry schedule records retry status and applies provider-header or exponential delay (`:176-198`).
- The production caller is `packages/opencode/src/session/processor.ts:627-675`: the LLM stream is drained and wrapped in `Effect.retry(SessionRetry.policy(...))`, so a transient provider failure replays the production stream instead of ending the turn immediately.
- The checked-out source labels itself 1.18.13, so an exact installed-1.18.18 black-box probe is recorded separately below before implementation is considered verified.
- `.omo/refs/jcode/crates/jcode-provider-anthropic-runtime/src/lib.rs:1489-1685` independently shows the intended Rust shape: finite `MAX_RETRIES`, retry only for classified transient failures, emit `RetryRollback` after partial output, and surface the final error. `jcode-message-types/src/lib.rs:713-719` defines rollback as discarding attempt-local text/tool/reasoning before replay.

Choice
------
- **Option A — wire it.** Upstream production retries transient provider failures, so removing the policy would create a known parity gap. This port will keep a finite budget, route replay through the existing `RetryRollback`/`StepAccumulator::reset_generated` seam, avoid retrying permanent failures, preserve already-emitted provider events for interfaces, and surface the final provider failure.

Implementation and focused regressions
--------------------------------------
- `run_turn` now invokes `retry_provider` around each provider stream with a finite three-attempt `ProviderRetryPolicy`. The identical prepared request is replayed, ordinary stream events remain incremental, and every retry emits `RetryRollback` through the same bounded `TurnEvent` channel before sleeping and replaying.
- The existing `StepAccumulator::reset_generated` consumes that rollback and clears text, reasoning, provider reasoning, tool calls, active tool state, finish state, and token accounting from the failed attempt. The successful replay is the only attempt checkpointed.
- Final transient exhaustion is unwrapped back to the final typed `ProviderError`, and permanent failures return after one request. No error-string classification or dependency was added.
- A typed compatibility edge preserves todo 154/166: a status-less transient after generated text/reasoning/tool output is surfaced immediately without rollback or replay. HTTP failures such as 503 carry `status=Some(503)` and remain retryable even if the failed attempt emitted partial output.
- Focused command: `CARGO_TARGET_DIR=/tmp/opencode/fu1 cargo test -p oc-engine --test loop loop_provider_retry --offline` -> 3 passed, 0 failed. The tests prove partial 503 rollback and replay, three-attempt exhaustion with the final 503 surfaced, and no replay for a permanent 400.
- Idle-timeout regression: `CARGO_TARGET_DIR=/tmp/opencode/fu1 cargo test -p oc-cli a_stalled_provider_ends_a_real_turn_with_partial_text_and_a_visible_idle_error --offline` -> 1 passed, 0 failed. `PARTIAL_T166` remained the only visible text and no `RetryRollback` appeared.
- Timing bound: a compatible-provider stall after partial output still costs one idle window. Before any generated output, three status-less transient stalls can consume three windows plus 2s + 4s backoff: about 366s at the 120s default, or about 546s at the compatible transport's 180s override cap. The budget is finite; it cannot wait indefinitely.
