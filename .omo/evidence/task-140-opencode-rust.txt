1. THE ROUTE CHOSEN, AND WHY IT IS THE HONEST ONE
--------------------------------------------------------------------------------
The todo offered three routes: implement the lifecycle, declare a divergence with a
witness, or record a NAMED COMPATIBILITY GAP.

  CHOSEN: named compatibility gap `assistant-turn-step-parts`.

The deciding fact is not "we did not get to it" — it is that the port ALREADY has
the implementation and merely never wired it up:

  * `oc-db` models both types as first-class serialized wire tags, not as strings
    in a fixture: `PartKind::StepStart` / `PartKind::StepFinish`
    (crates/oc-db/src/message.rs:139-142) tagged `"step-start"` / `"step-finish"`
    (:181-182), inside the documented 12-member part union (:24-33).
  * `oc_engine::stream::StreamProjector` already writes upstream's exact shape,
    including the snapshot hashes on both boundaries
    (crates/oc-engine/src/stream.rs:211-265 writes `step-start` at `start()`;
    :869-894 and :966-977 carry the snapshot hashes; :897-914 even emits the
    separate `patch` part).
  * But `StreamProjector::start` has NO production caller. The live turn path is
    `run_turn` -> `StepAccumulator::apply` -> `checkpoint_assistant`
    (crates/oc-engine/src/loop.rs:625-749), and `checkpoint_assistant` can only
    write `text` (:1547-1562), `reasoning` (:1563-1584) and pending `tool`
    (:1585-1588). Nothing else.

An unwired implementation is work outstanding, not a decision. `docs/divergences.toml`
says so in its own header — "An entry belongs here only when the difference is a
DECISION. A surface that is merely unimplemented is a gap, not a divergence: it is
reported by the suite's `not_compared` / `known_gaps` sections and must NEVER be
laundered into an entry here" — and `crates/oc-testkit/src/divergence.rs:26-31`
repeats it. Declaring this as divergence 18 would have been exactly that laundering.
So `DECLARED_COUNT` stays at 17 and `docs/divergences.toml` is unchanged.

Implementing it was rejected as the wrong task, not as too much work: `step-finish`
requires `reason`, `cost` and a structured `tokens` object
(packages/schema/src/v1/session.ts:240-257), the snapshot fields are what upstream's
diff/revert bounds are computed from, and wiring `StreamProjector` into `run_turn`
replaces the production turn loop's persistence path. That is a feature commit under
a `docs:` subject line, in a wave where three other tasks run in parallel over the
same crates. The gap now names it as outstanding, with the consumer impact measured.


2. WHAT THE UPSTREAM AND PORT SHAPES ACTUALLY ARE (RE-DERIVED, NOT INHERITED)
--------------------------------------------------------------------------------
Upstream, for one plain single-step turn — one user text, one assistant text reply,
no tools, no file changes — persists three assistant parts in this order:

    step-start   text   step-finish

  * `start-step` writes `step-start` UNCONDITIONALLY: the processor calls
    `snapshot.track()` first, but the `session.updatePart(...)` on the next line runs
    whether that returned a hash or `undefined`
    (packages/opencode/src/session/processor.ts:424-432). Snapshots are only enabled
    for a git project with snapshots not disabled
    (packages/opencode/src/snapshot/index.ts:167-170), and `track()` returns
    `undefined` otherwise (:318-323). So a non-git project still gets `step-start`,
    just without the `snapshot` field. This independently CONFIRMS todo 136's
    "reproduced inside a git repository and outside one" and rules out the
    "step-start only carries a snapshot" explanation.
  * the text deltas accumulate into ONE `text` part rather than several (:486-530).
  * `finish-step` appends `step-finish` (:435-455).
  * `patch` appears only when `patch.files.length > 0` (:457-468), so a plain turn
    has none.

This port persists one assistant part: `text`. Measured, not assumed — see section 4.

Consumer impact, so the gap says what is lost rather than only what is absent:
  * `step-finish.cost` / `.tokens` is the ONLY source upstream's projector reads to
    aggregate session usage (packages/core/src/session/projector.ts:36-42, applied at
    :90-108 and :325-328).
  * the first `step-start.snapshot` and the last `step-finish.snapshot` are the two
    bounds of a turn's diff (packages/opencode/src/session/summary.ts:82-99), which
    `revert` refreshes (packages/opencode/src/session/revert.ts:70-77). Note the file
    restore itself uses `patch` parts (:45-52), so this is the DISPLAYED diff.
  * `run --format json` emits both as `step_start` / `step_finish` stream events
    (packages/opencode/src/cli/cmd/run.ts:740-746).
  * the current App deliberately SKIPS both when rendering
    (packages/app/src/context/server-session.ts:26-31), so no TUI regression follows.

Interoperability is unaffected, and that was measured rather than hoped: every
assertion in `crates/oc-testkit/tests/session_interop.rs` holds across this
difference in both directions (todo 136).


3. A SECOND INSTANCE OF THE EXACT DEFECT F4 PUNISHES, FOUND WHILE DOING THIS
--------------------------------------------------------------------------------
The todo said to put the classification "in the current compatibility artifact".
Doing that surfaced a hole the todo did not name.

`docs/divergences.md` promises TWICE that a gap is "reported as `known_gaps` by the
compatibility report AND LISTED IN THE COMPATIBILITY MATRIX" (:3-6 and :135-140).
`docs/compatibility-matrix.md` HAD NO GAP SECTION AT ALL. The gap list was a private
`fn known_gaps()` inside `crates/oc-testkit/tests/compat_suite.rs`, reachable only
through `target/compat/compat-report.json` — a build artifact nothing commits and no
reader of the repository ever sees. So for the three gaps that already existed, that
sentence was already false, and nothing could fail over it.

This is structurally identical to the two defects F1 and F4 each rejected: a number
or a claim that was correct in the executable gate and stale in prose nothing
derived (`known_gaps()` saying 14/44, the README saying "thirteen"). Recording the
turn-part gap only in `compat_suite.rs` would have satisfied the letter of this todo
and reproduced the defect a fourth time.

So the fix is structural, not additive:
  * the gap list moved to `oc_testkit::compat_report::known_gaps(api_gap_count,
    upstream_api_operations)` — a library function, so more than one consumer can
    render it. The three existing entries moved VERBATIM; only the redundant
    `.to_owned()` on a `format!` result was dropped.
  * `compat_suite.rs::known_gaps()` is now one line calling it with
    `FROZEN_API_GAPS.len()` and `UPSTREAM_API_OPERATIONS`, so the report is unchanged
    in content.
  * `docs/compatibility-matrix.md` gained a `## Known gaps` section with a
    `<!-- generated:BEGIN known-gaps -->` block, generated by
    `crates/oc-cli/tests/docs.rs::known_gaps_block` from the SAME library function,
    using the API counts that test PROBES OFF THE RUNNING SERVER — not constants
    restated there. An API gap closing therefore rewrites this page without anyone
    editing it, and the docs gate fails until it is regenerated.

The classification appears in EXACTLY ONE place: `known_gaps()`. The matrix page and
`compat-report.json` are both renderings of it. It is NOT in `docs/divergences.toml`
(that would be the laundering) and NOT in `behavioural_differences()` (that structure
requires a `declared_as` resolving to an allow-list entry, and there is none).
