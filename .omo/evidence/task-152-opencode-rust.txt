THE DEFECT F4 FOUND
--------------------------------------------------------------------------------
Todo 148 registered eight wire-family factories, but `model_spec` built
`Spec::new(registry_key)` from the *generic* factory key. So OpenRouter became
`openai-compatible`, `family::resolve` picked the generic row instead of the
`openrouter` profile (whose `routes_upstreams` behavior differs), and the Azure
selector and Copilot model-dependent rule were unreachable. Separately
`provider_key_for_npm` rejected `@ai-sdk/groq` and `@ai-sdk/mistral`, which are
real rows in the pinned catalog and frozen members of todo 94.

THE FIX
--------------------------------------------------------------------------------
Factory selection and provider identity are now separate concerns
(`crates/oc-cli/src/cmd/turn.rs:1384-1386`):

    let mut spec = Spec::new(&model.provider_id)   // real identity
        .with_factory(factory_key)                 // wire family
        .with_surface(surface);

`COMPATIBLE_TRANSPORTS` (`turn.rs:1007-1022`) is a deliberately **closed**
`(identity, transport)` table covering all fifteen identities todo 94 froze:
alibaba, azure, cerebras, cohere, deepinfra, github-copilot, gitlab, groq,
mistral, openrouter, perplexity, togetherai, venice, vercel, xai.

The code comments why it is closed rather than transport-only: matching only the
transport "would admit an arbitrary provider id into a profile it did not" claim.
An unknown transport is still refused by name (`turn.rs:1378`), which todo 94
explicitly requires — no catch-all guess.
