SHARED TURN AND COMPACTION PATHS

`oc-server` owns the `SessionMutationExecutor` boundary. The production `serve`
composition root injects an executor implemented with `TurnPlan` and `TurnHost`.
HTTP prompt execution calls `TurnHost::drive_with_message_id`, which persists the
user message and invokes the existing `oc_engine::loop::run_turn`; no turn logic is
copied into the server. HTTP compaction calls `TurnHost::compact`, which reaches
`compact_manually` and the existing `run_compaction` implementation.

Prompt execution holds one `SessionRunGuard`, passes that guard's exact interrupt
signal into the production turn host, and forwards the bounded engine event channel
through `EventFanout`. The guard is released only when both execution and event
forwarding finish.

WAIT AND INTERRUPT

`SessionRunRegistry::wait_until_idle` uses `tokio::sync::Notify` with a
register-before-recheck loop, so it neither busy-polls nor loses a completion that
races registration. Guard drop notifies waiters. `/interrupt` fires the same live
guard signal that `run_turn` selects against while reading the provider stream.

The production-binary regression test starts a provider that sends HTTP/SSE headers
and then leaves its body open. It proves `/wait` remains pending while the turn is
active, `/interrupt` releases it, and persistence contains exactly one user row and
one completed assistant abort checkpoint. The assistant points to the real user row,
has `AbortError` plus `time.completed`, has no invented partial part, and the database
contains zero orphan parts.

CLI / HTTP ENTRY-POINT EQUIVALENCE

`crates/oc-cli/tests/session_mutation.rs` launches the real `opencode-rust run` and
`opencode-rust serve` binaries against two isolated databases containing the same
fixed session. Both entry points consume the same recorded
`openai-chat/streams-text` cassette. The test asserts:

  * both entry points produce the same assistant text;
  * the CLI stdout equals the persisted assistant text;
  * normalized session, message, and part semantics are identical; and
  * each entry point issues exactly one real provider request.

AGENT, MODEL, AND REVERT GUARDS

Agent, model, revert stage, revert clear, and revert commit all require an idle
session. Agent/model selection is persisted with the session update timestamp.
Revert stage validates that its boundary message exists and stores the marker;
clear removes it; commit atomically truncates legacy and projected history plus
context/input state after the staged boundary. Commit without a staged marker is an
idempotent 204 no-op rather than an unguarded destructive action.
