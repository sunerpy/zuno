investigated first. It is blocked by file ownership, not by capability:

  `completion` is pinned as pending in two places inside `crates/oc-cli/tests/surface.rs`,

The narrower reading also holds: the defect QA reported is that **`--help` promised what
the handler refused**, and that is fixable entirely inside `command.rs`, which is this
task's. Fixing it here does not foreclose (a); it makes the promise honest until whoever
owns the dispatcher surface can implement it.

Registered because upstream registers it, but it cannot emit a completion script. Upstream's script is a yargs shell function that asks the binary back for candidates over `--get-yargs-completions`; this port serves no such protocol, so a script emitted here would answer every request with nothing. THE GENERIC ASSERTION — crates/oc-cli/tests/help_honesty.rs
------------------------------------------------------------
Deliberately not a `completion` special case. Every check iterates
`oc_cli::PENDING_COMMANDS`, so the next command added to that roster inherits all of
them without anyone remembering to.

Two predicates, applied to the description clap renders:

  states_unavailability(text)         — text contains one of
                                        ["unavailable", "not available", "cannot",
                                         "unsupported"]
  opening_capability_promise(text)    — text's first word is one of 30 capability verbs
                                        ("generate", "print", "export", "emit", "write",
                                         "create", "output", ...)

Five tests:

  help_no_pending_command_advertises_a_capability_it_refuses
      For every PENDING_COMMANDS entry, both the root-listing description (`get_about`)
      and the own-help description (`get_long_about` falling back to `get_about`) must
      state unavailability and must NOT open with a capability verb. Both surfaces are
      checked because the defect appeared on both independently.

  help_no_rejected_command_opens_with_a_capability_promise
      The promise-verb half also applies to every `Disposition::Rejected` command. They
      all already open with "Explain", so this cost no rewording and closes the cheaper
      half of the same hole — a rejected command is registered and its listing reads
      exactly like a working one's.

  help_the_checked_claims_are_the_rendered_ones
      Runs the real binary. Asserts `--help` exits 0 and its whitespace-normalized
      output contains the checked root description, and that `<cmd> --help` exits 0 and
      contains the checked long description. Without this the predicates would prove a
      struct field, not a user-visible line: a hidden or overridden description could
      satisfy them while the terminal showed something else.

  help_every_pending_command_behaves_as_its_help_describes
      Runs the real binary twice per pending command — bare, and with one argument,
      because the reported defect was found by passing one. Asserts: exit != 0, stdout
      empty, stderr contains the recorded `PENDING_COMMANDS` reason verbatim, and stderr
      itself states unavailability. This is the "help and behaviour agree" direction.

  help_failure_scenario_the_shipped_promise_is_rejected
      The negative control, in the repo's established convention. Feeds the literal
      shipped string "Generate shell completion output" through both predicates and
      asserts the marker check rejects it and the promise check identifies "generate";
      then feeds the current description and asserts the opposite. Without it, both
      checks above would keep passing if the predicates were weakened to accept
      anything, since the roster's only entry happens to be worded correctly today.

Why the description is read structurally (`get_about` / `get_long_about`) rather than by
parsing the rendered `--help` columns: column parsing is fragile against clap's wrapping
and would have to guess where one command's entry ends. Reading the structured value and
then asserting the rendered output *contains* it, whitespace-normalized, gets both
exactness and rendered-truth without a parser.

WHY THE EXISTING TESTS COULD NOT SEE THIS
------------------------------------------
`crates/oc-cli/tests/surface.rs` has five disposition tests and every one of them passed
throughout the defect. They compare the disposition table, `PENDING_COMMANDS`, and the
dispatch arm against each other. All three were correct and mutually consistent:
`completion` really is pending, really is recorded as pending, and really does reach
`PendingCommandDispatcher`. None of them reads the help a user reads first, so the one
inconsistency that mattered — the description promising output — was invisible to all
five. This is the same shape as the `export` defect (todo 116) and as SEAM #11: several
mechanisms agreeing with each other while none of them touches the surface the user
touches.

Note also that `completion` has no row in `crates/oc-cli/src/disposition.rs` at all,
because upstream registers it through yargs' built-in `.completion()` rather than as a
`*Command` class, so it is absent from `tests/fixtures/upstream-commands-1.18.13.txt`
(23 symbols, none of them `CompletionCommand`). `disposition_for("completion")` returns
`None`. Every disposition assertion about it is therefore vacuously satisfied — a second,
independent reason no existing test could have caught this.

HONEST GAPS
-----------
- `completion` still emits no completion script. This change makes the promise honest;
  it does not deliver the capability. (a) remains the better end state and is unblocked
  on the dependency question — it needs `tests/surface.rs` and `src/cmd/mod.rs`, which
  todo 124 owns this wave.
- The ~100-minute memory gate and the 2-hour soak were not run; `oc-testkit` suites ran
  with `OC_MEMORY_GATE_MODE=skip` as instructed.
- The marker vocabulary is four phrases and the verb list is thirty words. Both are
  judgement surfaces: a pending command whose help says only "this is a no-op" would
  pass the marker check while arguably still misleading. The lists are deliberately
  short — a longer marker list starts accepting text that merely sounds cautious — and
  the negative control pins that they reject the one line known to have misled a reader.
- `help_every_pending_command_behaves_as_its_help_describes` invokes each pending command
  bare. A future pending command with a *required* positional would exit 2 from clap and
  fail this test rather than reporting the recorded reason. That failure is the correct
  outcome: it forces the decision about what such a command should print, instead of
  silently exempting it.
