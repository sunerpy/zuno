Commit: fix(cli): write session.model in upstream's shape


1. THE DEFECT
--------------------------------------------------------------------------------
`crates/oc-cli/src/cmd/turn.rs:1175` wrote the session `model` column as

    {"providerID": …, "modelID": …}

Upstream's *session* schema names the model `id`, not `modelID`. Its decoder reads
`row.model.id` (`packages/opencode/src/session/session.ts:88-93`), so the missing
key produces `Expected string, got undefined` and exit 1 — for the **entire**
listing, not just the offending row. A user who ran one Rust turn and then rolled
back to the release could no longer list any session in that database.

The *message* record at `turn.rs:1198` was already correct and is unchanged.

3. THE OPEN QUESTION: IS `variant` OPTIONAL?  — YES, AND IT IS OMITTED
--------------------------------------------------------------------------------
Answered from upstream's schema, not inferred.

  /config/workspace/ProdDir/AI/opencode/packages/opencode/src/session/session.ts:220-224

      const Model = Schema.Struct({
        id: ModelV2.ID,
        providerID: ProviderV2.ID,
        variant: optional(Schema.String),
      })

`id` and `providerID` are REQUIRED; `variant` is `optional(...)`. Corroborated in
the data: absent from 197 of 5,961 rows.

  $ sqlite3 -readonly … "SELECT SUM(json_extract(model,'\$.variant') IS NULL),
                                SUM(json_type(model,'\$.variant')='null'),
                                COUNT(*) FROM session WHERE model IS NOT NULL;"
  197|0|5962

Note the second column: **zero** rows store an explicit JSON `null`. Upstream
either writes a string or omits the key. Its writer passes `info.model` straight
through (`session.ts:130`), so an absent TypeScript `variant` never becomes
`null` on disk.

DECISION: `variant` is omitted, not emitted as null. Reasons —
  (a) the schema marks it optional, so omission decodes;
  (b) 197 real rows already omit it, so the release demonstrably accepts that;
  (c) zero real rows contain `"variant":null`, so writing null would be a shape
      no upstream row has, i.e. exactly the one-field-over version of this bug;
  (d) nothing in this port has a variant to record at session-creation time —
      `TurnPlan` carries `provider_id` and `model_id` only.

Asserted by name in `oc-cli/src/cmd/turn_tests.rs::a_persisted_session_names_its_
model_id_the_way_upstream_reads_it`, so a later edit cannot start writing null.

The corresponding *message* schema, for contrast:

  packages/opencode/src/session/message.ts:121-125
      assistant: Schema.optional(Schema.Struct({
        system: Schema.Array(Schema.String),
        modelID: ModelV2.ID,
        providerID: ProviderV2.ID,
        …

`modelID` there, `id` in the session struct. Same concept, two spellings, one
file apart.

5. THE FIX
--------------------------------------------------------------------------------
crates/oc-db/src/session.rs — new `pub fn model_reference(provider_id, model_id)
-> String`, documented beside the column with the upstream citations, the row
counts, and the `variant` decision. Serialised through `serde` (no hand-rolled
escaping).

crates/oc-cli/src/cmd/turn.rs:1174-1177 —

  +        &plan.provider_id,

7. THE COMPAT SUITE'S BLIND SPOT, CLOSED
--------------------------------------------------------------------------------
`journal_round_trip_through_the_real_binary_does_not_replay_migrations` passed
throughout this defect's life because it opens an **empty** Rust database and
checks the `migration` table. It never asked the release to decode a row a Rust
turn wrote. Strengthened rather than left as-is:

  crates/oc-testkit/tests/compat_suite.rs::a_session_written_by_this_port_is_
  decodable_by_the_real_binary   (+ registry row `db-session-decode`)

  It lets the ORACLE create the database and resolve its own project, writes one
  session through the production writers (`oc_db::session::create` +
  `model_reference`), then re-runs `session list` on the release.

  A first draft invented its own project row. It exited 0 with an EMPTY listing —
  `session list` is scoped to the project resolved for the directory it runs in,
  so a made-up project id silently disarmed the test. Caught because the
  session-id assertion failed, and recorded in the helper's doc comment so a
  later simplification cannot re-disarm it. This is the same
  fixture-supplies-what-real-input-lacks trap logged four times before.

  Proven to bite — `model_reference` mutated back to the `modelID` spelling:
