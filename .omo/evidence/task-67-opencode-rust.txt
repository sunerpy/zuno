WHERE THE GOAL TABLE LIVES, AND WHY
-----------------------------------
Its own SQLite file: `$XDG_DATA_HOME/opencode/goal_1.db`, beside `opencode.db`
and not inside it. Objective spill files: `$XDG_DATA_HOME/opencode/goal-objective/<uuid-v4>/goal-objective.md`.

Two independent reasons, either sufficient:

1. `opencode.db` is not ours to extend. oc-db reproduces the TypeScript
   `opencode.db` byte-for-byte — 19 application tables plus the `migration`
   journal — and proves it with a differential test against a real database
   (crates/oc-db/src/schema.rs, crates/oc-db/tests/schema.rs) plus a 38-entry
   journal contract (crates/oc-db/src/migration/mod.rs:10-52). A 20th table
   breaks that test, and the promise it guards: that a user can switch between
   the two binaries and keep their sessions. A goal is a feature the TypeScript
   binary does not have.
2. A goal must outlive session churn. Its whole purpose is to survive the
   compaction that discards the conversation which set it, so it must not share
   a file with state that gets pruned, vacuumed and cascaded. There is therefore
   deliberately NO `FOREIGN KEY (session_id) REFERENCES session(id) ON DELETE
   CASCADE` — a goal is keyed *by* a session id, not owned by a session row.
   Proven by store::tests::the_table_declares_the_check_constraint_and_deliberately_no_foreign_key
   (`pragma_foreign_key_list('goal')` returns 0 rows; the DDL contains no
   "FOREIGN KEY"; the database holds exactly 1 table).

codex reached the same place by the same route: goals live in their own
`goals_1.sqlite` (codex-rs/state/src/sqlite.rs:30) and there is a
`0034_drop_thread_goals.sql` in the *main* migration set recording the move out
of the shared state database.

THE OWNERSHIP SPLIT, AND HOW IT IS ENFORCED
-------------------------------------------
Structurally, by two distinct types — not by a runtime check a future caller can
forget, and not by a doc comment:

  ModelStatus  = { blocked, complete }                       (status.rs)
  SystemStatus = { active, paused, usage_limited, budget_limited }

`GoalStore::update_status_as_model` takes a `ModelStatus`. There is no `paused`
variant to pass; the type cannot represent the request. `set_status_as_system`
takes a `SystemStatus`, and no model-facing API produces one.

`active` is SYSTEM-owned. The model already obtains `active` by creating a goal,
so making it model-writable buys nothing and opens a hole: a model on a
`budget_limited` goal could set `active` and keep spending. Recorded in
decisions.md.

Belt and braces: both status statements re-derive the budget limit in SQL, so
even a *system* reactivation of an over-budget goal lands back on
`budget_limited` (see section 4 of the matrix below). The type system stops the
model from asking; the SQL stops anyone from succeeding.

THE REFUSAL MESSAGES, VERBATIM
------------------------------
  goal status `paused` is the system's to set, not the model's; the model may set only `blocked` or `complete`
  unknown goal status `halted`; expected `blocked` or `complete`
  session ses_goal_matrix already has a goal with status `active`; create_goal may replace a goal only once it is `complete`

HOW THE TWO INVARIANTS WERE MADE ATOMIC IN SQL
----------------------------------------------
Guarded replace — one upsert whose DO UPDATE carries the guard, ports
codex-rs/state/src/runtime/goals.rs:245. When the WHERE is false SQLite skips
the row, RETURNING yields nothing, and there is no separate read a concurrent
writer could slip between:

  INSERT INTO goal (...) VALUES (?1, ?2, ?3,
      CASE WHEN ?4 IS NOT NULL AND 0 >= ?4 THEN 'budget_limited' ELSE 'active' END,
      ?4, 0, 0, ?5, ?5)
  ON CONFLICT(session_id) DO UPDATE SET
      goal_id = excluded.goal_id, objective = excluded.objective,
      status = excluded.status, token_budget = excluded.token_budget,
      tokens_used = 0, time_used_seconds = 0,
      created_at_ms = excluded.created_at_ms, updated_at_ms = excluded.updated_at_ms
  WHERE goal.status = 'complete'
  RETURNING ...

The subsequent read of the blocking status happens inside the SAME transaction
as the refusing statement, so it only *names* the blocker; it never decides.

Budget flip — carried by every statement that can move `tokens_used` or
`token_budget`, ports goals.rs:546-566 and goals.rs:618-630. `tokens_used + ?1`
reads the pre-update value, so the flip decides on the post-increment total
inside the statement performing the increment:

  UPDATE goal
  SET tokens_used = tokens_used + ?1,
      time_used_seconds = time_used_seconds + ?2,
      status = CASE
          WHEN status = 'active' AND token_budget IS NOT NULL
               AND tokens_used + ?1 >= token_budget THEN 'budget_limited'
          ELSE status
      END,
      updated_at_ms = ?3
  WHERE session_id = ?4
  RETURNING ...

The same CASE appears in `set_token_budget` (lowering a budget below the spend
stops the goal in one statement) and in `set_status_as_system` (an `active`
request on an over-budget goal resolves to `budget_limited`). And the upsert's
`0 >= ?4` is `status_after_budget_limit(Active, 0, budget)` in SQL, so a budget
of Some(0) can never be observed as an `active` goal.

Two tests run the statement text DIRECTLY against a connection, with none of
this crate's Rust in the path, because a test that only calls the store cannot
tell a SQL `WHERE` from a Rust `if` wrapped around an unguarded statement:
  store::tests::the_replacement_guard_is_in_the_statement_and_not_around_it
  store::tests::the_budget_flip_is_in_the_recording_statement_and_not_around_it

THE OBJECTIVE CAP AND SPILL
---------------------------
MAX_OBJECTIVE_CHARS = 4,000, counted with `chars().count()` (not bytes), porting
codex-rs/protocol/src/protocol.rs:4076-4082. codex splits this across two layers
— the protocol *rejects* an oversized objective and the TUI
(codex-rs/tui/src/goal_files.rs:121-136) spills before calling — which means
every future caller must remember to spill. Here both live BELOW the store's
API, so the column's contract (never longer than 4,000 chars) holds for callers
that have never heard of a spill file.

The pointer sentence written into the column:

  Read the full goal objective at <spill_dir>/<uuid-v4>/goal-objective.md before continuing.

Observed for a 5,500-character objective (section 5 below):

  submitted objective: 5500 characters
  stored objective:    121 characters
  stored objective:    Read the full goal objective at /tmp/.tmpoWHZbT/80d708da-926e-433e-a72d-9729a6219cfe/goal-objective.md before continuing.

Reading the pointer back VALIDATES rather than merely parses — inside the spill
dir, named `goal-objective.md`, parent directory a v4 UUID (porting
goal_files.rs:164-171). Without those three checks a model-authored objective
would be an arbitrary-file-read primitive; spill::tests::a_pointer_the_model_forged_is_refused_on_all_three_checks
covers all four forgeries.

TRANSITION MATRIX
-----------------
Sections 3 and 4 below are the machine-generated matrix, one line per
(from-status, to-status, actor). 72 rows with no budget (6 x 6 x 2) and 60 rows
with the budget already spent (5 x 6 x 2; `active` is not a reachable seed under
a spent budget, because the flip fires the moment the counters cross). 132 rows
total, 66 of them refusals. Every refused write is additionally asserted to have
left the row untouched.

Summary of the shape, per from-status:
  model  -> blocked, complete                      ALLOWED
  model  -> active, paused, usage_limited, budget_limited
                                                   REFUSED, naming `blocked` or `complete`
  system -> active, paused, usage_limited, budget_limited
                                                   ALLOWED
  system -> blocked, complete                      REFUSED (model-owned; SystemStatus cannot represent them)
Two SQL guards then modify the ALLOWED outcomes:
  budget_limited -> blocked (model)  stores budget_limited  (goals.rs:328)
  budget_limited -> paused  (system) stores budget_limited  (goals.rs:293)
  * -> active (system), counters over budget, stores budget_limited  (goals.rs:329)
  budget_limited -> complete (model) stores complete — finishing the work is true
  regardless of what it cost.

WHAT THE PLAN GOT WRONG, AND WHAT IT DELIBERATELY DIVERGED ON
-------------------------------------------------------------
Nothing in the plan was wrong. Two deliberate divergences from codex, both of
which the plan is right about:

1. The plan requires `create_goal` to replace only a `complete` goal. The prompt
   says codex's `replace_thread_goal` (goals.rs:156-210) has no status guard —
   true, but codex has a SECOND function, `insert_thread_goal` (goals.rs:213-269),
   whose upsert carries exactly `WHERE thread_goals.status = 'complete'`
   (goals.rs:245). So the guard the plan asks for is codex's, in codex's own SQL;
   what codex leaves to convention is *which* function the model reaches. This
   crate moves that from convention into the API's names: `create_goal`
   (guarded, model-facing) versus `replace_goal_as_system` (unguarded, the
   user's escape hatch — without it a `blocked` goal would be permanent, since
   no system status is `complete` and `create_goal` refuses).
2. The two-scope ownership split is genuinely absent from codex; codex lets any
   caller name any status and repairs the outcome in SQL. The plan wins.

One nuance worth recording: codex needs a four-valued
`GoalAccountingMode` (goals.rs:33-38) to decide whether a non-active goal
accrues usage. Here the counters always accrue — a counter that stops counting
is a counter nobody can trust, and a turn that finished the goal still had a
cost — while only the FLIP is restricted to `active`, matching
goals.rs:526-531. So a completed goal records its final cost without being
relabelled `budget_limited`
(store::tests::usage_accumulates_for_a_finished_goal_without_reviving_the_budget_flip).
