# opencode-rust - Work Plan

## TL;DR (For humans)

**What you'll get:** A Rust rebuild of the opencode command-line tool that you can swap in for the one you use today. It reads the same settings files, accepts the same commands, serves the same web interface, and shares the same session database — so you can switch back and forth, and switch back if you don't like it. Your existing sign-in plugins keep working unchanged, so your usual models are available on day one. It adds three things the current tool doesn't have: a leaner built-in team of assistants you can steer per task (which model, how hard it should think), a goal document that keeps a long job on track even when the conversation gets summarized away, and housekeeping commands to see every past conversation across all your projects and clean out old ones safely.

**Why this approach:** You're switching because the current tool eats memory and freezes. So memory and responsiveness are treated as things the project must *prove*, not hope for: it gets measured against the current tool on the same work, counting every helper process it starts, and there's a check that fails if a job ever goes quiet for too long. The rebuild also deliberately copies only the *outside* of the current tool — the files and commands you interact with — and rebuilds the inside cleanly, because two other Rust projects that tried this took shortcuts we can now avoid.

**What it will NOT do:** It won't support the old, retired ways of writing settings — if you have an outdated setting it will tell you what to change instead of quietly ignoring it. It won't include the website, desktop app, or the paid cloud features. It won't look pixel-for-pixel like today's terminal interface, though it will do the same things.

**Effort:** XL — 97 pieces of work across 14 stages. This is a large rebuild of a substantial tool, not a weekend project. Be aware that a few of those pieces are still big enough to be split again once work starts; both reviewers flagged that the count understates the terminal-interface and provider work in particular.
**Risk:** High — the main risk is that "compatible" is a big promise; the plan handles it by testing the new tool against the real one on every surface rather than trusting that they match.

**What the two independent reviews changed:** both reviewers blocked the first version. The important ones: the memory and hang tests could have been graded on a curve set after seeing the results, so the measurement rules and pass formulas are now fixed up front and the current tool is measured first, in the very first stage; the "same web interface" promise was written as an impossible equality (it can't both match exactly and add the new cleanup commands), so it now reads "everything the old one serves, plus the new bits, listed"; and one requirement was based on a factual error I had recorded — a detail I attributed to the sign-in plugin's connection to this tool actually belongs to its own internal Amazon connection, so that test was replaced with one that checks the real behavior instead. Also: the provider work was one item pretending three different networks were the same, and is now four.

**Decisions to sanity-check:**
- The new tool will **report itself as version 1.18.13** where plugins check compatibility. Without this, your two sign-in plugins get skipped and you can't reach your models. Its real version is shown separately.
- Old/retired settings will **cause an error, not be ignored** — I judged a silent skip to be worse, because a setting that's quietly dropped looks like it's working.
- The built-in assistant team is **six roles, not omo's eleven**, and it no longer ships a hardcoded table of model names. Your assistants inherit whatever model you're using unless you pick a preset. This is the biggest change from what you use now.
- The "run code" tool follows jcode's approach as you asked, and the research found jcode has **no code interpreter at all** — it uses a shell plus a parallel tool-combining step. So that's what gets built, plus one addition jcode lacks that recovers most of the benefit.
- Deleting old conversations **shows you a preview by default** and needs explicit confirmation; archiving is offered first because it can be undone.

Your next move: approve, or ask for the two independent high-accuracy reviews before anyone writes code. Full execution detail follows below.

## Scope

### Must have

**Compatibility baseline.** `opencode 1.18.13` at commit `aefaf140c1` (branch `dev`) of `/config/workspace/ProdDir/AI/opencode`. That tree is read-only reference and test oracle; it is never modified. Compatibility is defined as observable behavior: files read and how they merge, CLI accepted, HTTP served, database and disk state written.

1. **C1 Compat brain** — the full config contract: 30+ top-level keys (`packages/core/src/v1/config/config.ts:32-190`), the 10-layer merge order with `instructions` de-dup-concatenation (`packages/opencode/src/config/config.ts:39-50`), `{env:VAR}`/`{file:path}` substitution (`config/variable.ts:33-90`), instruction-file discovery (`session/instruction.ts:60-168`), agent definitions from config and markdown (`config/agent.ts:11-58`, `core/src/v1/config/agent.ts:7-40`), skill discovery across six roots (`skill/index.ts:173-227`, `skill/discovery.ts:13-131`), command resolution precedence (`command/index.ts:65-152`), and the permission engine's `findLast` semantics with tool hiding (`permission/index.ts:28-219`).
2. **C2 Session engine** — one event-emitting turn loop reproducing `session/prompt.ts:1052-1347` and `session/processor.ts:98-683`; message/part model and SQLite persistence byte-compatible with `core/src/session/sql.ts:22-177`; compaction; snapshots; interrupt/abort.
3. **C3 Provider/LLM** — multi-provider streaming, reasoning/thinking effort mapping per `provider/transform.ts:721-1410`, prompt-cache prefix stability, and `auth.json` / `mcp-auth.json` at mode 0600 (`auth/index.ts:10-89`, `mcp/auth.ts:9-81`). **Coverage is committed by wire-protocol family, not as "the whole table".** `provider/provider.ts:107-134` bundles **23 distinct SDK factories** whose protocols genuinely differ — Bedrock needs SigV4 signing plus EventStream framing, Google Generative AI has its own request/response shape, Vertex adds GCP auth (plus a separate Vertex-Anthropic variant), Azure has its own model-selection rules (`:154-160`), Bedrock Mantle routes by model id (`:162-166`), and GitHub Copilot picks its endpoint per model (`:225-239`). One "OpenAI-compatible profile" cannot produce behavioral equivalence for those. Committed families: **F1** OpenAI (Chat Completions + Responses), **F2** Anthropic, **F3** Bedrock incl. Mantle, **F4** Google + Vertex + Vertex-Anthropic, **F5** Azure, **F6** genuinely OpenAI-compatible providers behind one configurable profile (OpenRouter, xAI, Mistral, Groq, DeepInfra, Cerebras, Cohere, TogetherAI, Perplexity, Vercel, Alibaba, GitLab, Venice, Copilot, Gateway). A provider whose family is not implemented is reported **unsupported, naming the family that would carry it** — never silently routed through a profile that cannot reproduce its behavior.
4. **C4 Tools and integrations** — all 17 built-in tools registered in `tool/registry.ts:96-247`; MCP client for stdio + Streamable HTTP + SSE with OAuth (`mcp/index.ts:212-370`); the 39 built-in LSP servers (`lsp/server.ts`) over JSON-RPC/stdio; ripgrep, PTY, tree-sitter shell analysis, and file watching as native replacements.
5. **C5 Extensibility** — a Rust-authorable plugin system with no `unsafe`: out-of-process JSON-RPC plugins (primary), optional in-process WASM components, and a JavaScript compat host that runs existing `@opencode-ai/plugin` modules so `opencode-antigravity-auth` and `@sunerpy/opencode-kiro-auth` continue to supply the user's models. All ~20 hooks of `packages/plugin/src/index.ts:222-335` are dispatchable.
6. **C6 Agents and goal** — a **slimmed** native port of omo's design (roster modeled on `oh-my-opencode-slim`, not a 1:1 copy of omo 4.21.0's ten agents), its `CATEGORY_MODEL_REQUIREMENTS` fallback table, and a `task` tool accepting agent type, category, model, reasoning effort, skills, background, and session continuation; plus a codex-style goal subsystem (SQLite authority, status ownership split between model and system, token/time budgets, idle self-continuation, completion-audit rubric) with a human-editable Markdown projection.
7. **C7 Interfaces** — the CLI command and flag surface of `packages/opencode/src/index.ts:45-103` and `src/cli/cmd/**`; the 61 `/api/*` endpoints from `packages/protocol/src/groups/*.ts` with generated OpenAPI, served as a **required subset** of what this binary exposes (C8 adds maintenance endpoints, so demanding set *equality* with upstream would be unsatisfiable by construction — every upstream path+method must exist, additions must be allow-listed); a ratatui TUI of equivalent capability; ACP per `packages/opencode/src/acp/agent.ts:32`.
8. **C8 Session maintenance (new capability)** — cross-project global session listing; age-based retention with archive and delete modes, scoped to one project or all projects; correct subtree handling for `parent_id` (which has no SQL cascade); reference-counted GC of off-database artifacts; explicit `VACUUM` with byte reporting. Preview is the default; deletion requires explicit confirmation.
9. **The database journal contract** — the `migration` table plus the 38 recorded migration ids, and the full 19-table schema. This is what makes side-by-side use and rollback real rather than claimed: `packages/core/src/database/migration.ts:19-40` replays any migration id absent from that table and wraps the whole thing in `Effect.orDie`, so a Rust-created DB without a prefilled journal makes the real TypeScript binary **die** on next open.
10. **The `execute` / code-mode tool, modeled on jcode — not on the TypeScript interpreter.** Upstream implements it as `packages/codemode/`, an in-process JS/TS interpreter (`acorn` + `typescript`, `src/interpreter/`) that exposes the agent's tools as callable functions to model-authored code (`tool/registry.ts:114,221,300-303`). A Rust binary that forbids `unsafe` and bundles no JavaScript runtime has no business hosting a TypeScript interpreter, so this project takes **jcode's** approach to "let the model run code that calls tools" instead. The mechanism jcode uses is the specification; the TS source is reference only for the tool's observable contract (id, description, parameter shape).
11. **omo's capability, built in and slimmed.** omo is treated as part of the product, not as a plugin to load: its agent roster, category→model/reasoning-effort table, `task` delegation surface, and goal/plan state layer are native. The set is deliberately **leaner than omo 4.21.0**, modeled on `oh-my-opencode-slim`; every dropped feature is recorded as a decision with a reason, never as a silent omission.
12. **The TUI configuration contract** — `theme` and `keybinds` do **not** live in the main config schema; they live in `packages/tui/src/config/{index.tsx,keybind.ts}`: **184 keybind entries**, **33 built-in theme JSONs** (`tui/src/theme/assets/`) with four-layer resolution (built-in + custom + plugin + system, `theme/index.ts:166-185`), plus `attention{enabled,notifications,sound,volume,sound_pack,sounds}`, `leader_timeout`, `prompt`, `scroll_speed`, `scroll_acceleration`, `diff_style`, `mouse`, `max_height/max_width`.
13. **Formatter execution and plan-file writing** — post-edit formatting (`packages/opencode/src/format/{index,formatter}.ts`), not merely formatter config parsing; and `.opencode/plans/<created>-<slug>.md` writing (`session/session.ts:331-335`) as a real deliverable.
14. **A versioned compatibility manifest, and a migration ceiling that refuses rather than corrupts.** Compatibility is a versioned capability, not a permanent property: the binary records the upstream commit it was verified against, the highest migration id it understands, the plugin package+version pairs it was tested with, and the provider cassette set. Opening a database whose journal contains an id above the recorded ceiling **refuses with a message naming the ceiling and the observed id** — it does not attempt to proceed. The documented rollback promise is scoped to pinned version pairs (this binary ↔ opencode 1.18.13), because a newer TypeScript binary can apply migrations this one does not know.
15. **A per-command disposition for every CLI command**, including the seven that were previously unaddressed: `export`, `import`, `upgrade`, `uninstall`, `stats`, `completion`, and `github`/`pr`. Note `cli/cmd/stats.ts` reads `@opencode-ai/core/session/sql` directly, so excluding the `stats` *package* does not cover the *command*.
16. **Non-functional acceptance with numbers** — a resident-memory ceiling expressed as a figure, measured against a same-workload baseline of the TypeScript binary, **counting child-process RSS** (LSP, MCP, PTY, plugin hosts) rather than only the Rust process; a soak run with a defined duration, turn count, and growth predicate; and a **liveness/hang watchdog assertion**, because replacing unbounded channels with bounded ones converts an out-of-memory failure into a blocking one, and "卡死" is half the reported symptom. Bounded channels on every producer/consumer boundary, each with a declared overflow policy.

### Must NOT have (guardrails, anti-slop, scope boundaries)

- **No legacy/deprecated compatibility** (user directive: 无需兼容老特性). Not implemented: `mode.<name>` config blocks; `{mode,modes}/*.md` agent directories; agent `tools: Record<string, boolean>`; agent `maxSteps`; the `layout` key; `autoshare`; `CONTEXT.md` as an instruction source; the global TOML `config` file; the JSON `storage/**` session layout and any migration from it; the duplicate `reference` spelling of `references`. Each of these has a **runtime-detectable input** and is therefore **rejected with an error naming its modern replacement** — never silently ignored, because a quietly-dropped config block presents as working while doing nothing.
  - **Two deprecated items are NOT in that rejection list, deliberately.** `AuthOuathResult` is a pure type alias (`packages/plugin/src/index.ts:220`) with zero runtime presence — there is nothing to detect, so claiming it is "rejected" would be a false promise. Auth-prompt `condition` does not come from a config file at all; it is a **JS closure** returned by a plugin's `auth` hook (`plugin/src/index.ts:102-103,115-116`) and only appears during `auth login`, so it belongs to the plugin-boundary decision (see the closure note under C5), not to config validation. Both were previously mis-scoped here; recorded so the error is not re-introduced.
- No port of `app`, `desktop`, `session-ui`, `ui`, `storybook`, `web`, `console`, `enterprise`, `function`, `slack`, `stats`, `containers`, `identity` (~385K of 562K LOC; none is in the CLI dependency closure).
- No hosted/cloud features: Console accounts, org config, billing, share publishing, `/sync/*`, `/experimental/control-plane/*`, GitHub App install.
- No pre-`/api/*` HTTP endpoints beyond the measured minimum the JS compat host provably requires. **Measured, not guessed**: the two auth plugins together use exactly six SDK methods — `client.auth.set`, `client.session.abort`, `client.session.messages`, `client.session.prompt`, `client.provider.oauth`, `client.tui.showToast`. The last is a `/tui/*` control endpoint and is explicitly **in** the minimum; a literal reading of "no pre-`/api/*` endpoints" would have deleted it and broken every plugin toast. **Correction carried from review:** `client.middlewareStack` is *not* part of this contract — that property belongs to an AWS `CodeWhispererStreamingClient` the Kiro plugin constructs internally (`.../opencode-kiro-auth/dist/plugin/sdk-client.js:18,33,40`), and the plugin's only use of the opencode SDK client is `showToast` (`dist/plugin.js:46`). An earlier draft required the compat host to expose `middlewareStack` on `PluginInput.client`; that was wrong and is removed.
- **The `/api` set is a required SUPERSET-compatible subset, never an equality claim.** Every upstream path+method must exist and behave; this binary additionally exposes C8 maintenance endpoints. Demanding set *equality* with upstream — as an earlier draft of the compat gate did — is unsatisfiable the moment C8 lands, and would have made the headline compatibility suite unpassable by construction. Additions are allow-listed and documented.
- No modification of `/config/workspace/ProdDir/AI/opencode`. Read-only oracle.
- No `unsafe` blocks in first-party crates. No OpenSSL. No bundled Node/Bun binary.
- No pixel-identical TUI reproduction; no reimplementation of OpenTUI.
- No self-authored-fixture-only protocol tests for MCP, LSP, ACP, or SSE. Every wire protocol is validated against a real counterpart. (claw-code shipped an MCP client using LSP `Content-Length` framing instead of NDJSON, with a fully green suite, because its fixtures shared the bug.)
- No implicit destructive behavior in C8: no prune without confirmation, no `VACUUM` without an explicit request, and no deletion of a mid-compaction or published session without an explicit override flag. **"Running" cannot be a DB-answerable predicate** — busy state is in-process only (`packages/opencode/src/session/run-state.ts:35-74`), so the guarantee is instead: probe a reachable server's `/api/session/active` and refuse those IDs; when no server is reachable, refuse any session whose `time_updated` falls inside a safety window (default 1h), crossable only with `--include-recent`.
- No reduced "MVP"/"v1" subset of the compatibility contract. Waves are execution ordering, not scope cuts.
- No `anyhow`-everywhere error handling, no hand-written JSON tool schemas, no rendering inside provider or tool code, no second turn loop, no `cfg!(test)`-conditional runtime behavior, no unbounded channels. Each is a named defect observed in a reference implementation.

## Verification strategy
> Zero human intervention - all verification is agent-executed.
- Test decision: **contract-first TDD** for every compatibility surface (config merge order, variable substitution, legacy rejection, permission `findLast`, command/skill precedence, DB schema and cascades, SSE framing, MCP framing, wire shapes). The test is written from behavior extracted from the TypeScript source or observed from the real binary **before** the Rust code exists, and must fail for the right reason first. **Tests-after** for internal plumbing (rendering, CLI wiring, logging).
- Frameworks: built-in `cargo test` for unit and integration; `insta` for snapshot assertions on merged config, rendered prompts, and CLI output; `proptest` for merge-order and permission-rule invariants; `wiremock` for HTTP provider tests; a first-party `oc-testkit` crate for the differential harness, cassette replay, and the mock provider.
- Differential oracle: `oc-testkit` drives the real `opencode` binary and the Rust binary over identical inputs (config trees, CLI invocations, HTTP requests, a temp `OPENCODE_DB`) and diffs normalized outputs. Provider traffic is replayed from `packages/llm/test/fixtures/recordings/`, never live.
- Protocol conformance: MCP against at least one real third-party server (the user's own `codegraph serve --mcp` and a remote HTTP server); LSP against at least two real servers; ACP against the real `@agentclientprotocol/sdk` client. Fixture-only validation is not acceptable evidence.
- **Non-functional gates — the reason this project exists, so these are numbered and falsifiable, not aspirational.** The stated motivation is that the TypeScript build exhausts memory and hangs, so every gate below must be able to FAIL, and each must be comparable against the TS binary on the identical workload. Four rules:
  1. **Total-process-tree RSS, not just our own.** Every measurement sums the Rust process **plus every child it spawns** (LSP servers, MCP stdio servers, PTY children, the JS compat host). Measuring only the parent produces a flattering number while the real footprint is unchanged.
  2. **Paired baseline.** Each workload runs against the real `opencode` binary and the Rust binary under identical env, and the report records both plus the ratio. A gate with no baseline cannot demonstrate the motivating fault is fixed.
  3. **Workloads must exercise the actual memory drivers**, which cassette replay does not: large `part.data` JSON hydration (open the largest session in a real `opencode.db`), tool-output store growth, a file watcher over a large repository, several concurrent LSP servers, PTY output volume, and SQLite WAL growth. Provider-traffic replay touches none of these.
  4. **A hang gate, because bounded channels convert OOM into blocking.** Replacing unbounded channels (a named defect of a reference implementation) trades one symptom for another; the new symptom must be tested or the trade is unverified.
  Concrete gates, each a test that fails when breached: **(G1)** idle steady state after startup + one trivial turn — total-tree RSS ceiling asserted, and asserted to be a stated fraction of the TS binary's on the same workload; **(G2)** largest-real-session hydration — RSS ceiling asserted, with the session id and its message/part counts recorded in the evidence; **(G3)** soak — a stated number of turns over a stated wall-clock duration with cassettes plus a live file watcher and two LSP servers, asserting RSS growth **slope** over a sliding window stays under a stated bound (not merely "no unbounded growth", which is not a predicate); **(G4)** liveness watchdog — a turn that makes no **state progress** for longer than the stated timeout fails the run, and the same watchdog runs inside G3; **(G5)** backpressure — a deliberately stalled consumer on every bounded channel must degrade by coalescing or blocking **with progress still observable elsewhere**, never deadlock, proven per channel; **(G6)** child-process reaping — after N sessions with LSP/MCP/PTY activity, assert zero orphaned children by PID enumeration.

  **The measurement methodology and the threshold FORMULAS are frozen here, before any Rust code exists, and measured in Todo 93 (Wave 1) — not in Wave 14.** An earlier version of this section deferred both the numbers *and* how they were derived to the end of the project, which meant a run could observe its own results and pick values that pass. That would have left the motivating problem unproven. Frozen now, and not renegotiable during execution:
  - **Workload definitions** (all three, fixed): *W-idle* = cold start, one turn of a single cassette-backed prompt with one tool call, then 60s settle. *W-real* = open the largest session in a read-only copy of the user's `opencode.db` (selected by `SUM(LENGTH(part.data))`, id recorded), render it, then one turn. *W-soak* = **≥ 500 turns** over **≥ 2 hours** wall clock, cassette-backed, with a file watcher on a ≥ 50,000-file tree, ≥ 2 real LSP servers, one tool call producing ≥ 50 MB, one PTY emitting ≥ 100 MB, and ≥ 1 compaction cycle.
  - **Sampling**: total-process-tree RSS (parent + all transitive children) sampled every **2s**; each of G1/G2 run **5 times**, the reported figure being the **median of per-run peaks**; both binaries measured under identical env, interleaved (alternating runs) to cancel machine drift.
  - **Warm-up discard applies to `W-soak` ONLY** — revision 2, corrected during execution with measured evidence, before any Rust code was measured. Revision 1 discarded the first 90s of *every* workload. For the two bounded cold-start workloads that is wrong by construction: the peak they exist to measure **is** the startup-plus-turn spike. Measured proof from todo 93's retained raw samples — `W-idle` spans only 148s, so a 90s discard drops 61% of the trace, and the median per-run peak falls from **932 MB (whole trace) to 729 MB (post-90s)**, i.e. the rule was hiding ~200 MB of real peak. `W-real` is unaffected (its 448s trace peaks after 90s either way). Because no Rust measurement existed when this was found, the correction cannot have been fitted to a result — which is exactly the case the `PERF_METHODOLOGY_REVISION` mechanism exists to permit.
  - **Threshold formulas** — Wave 14 may only substitute the measured TS values into these; it may not alter the formulas: **G1 pass** iff `median_peak(rust, W-idle) ≤ 0.50 × median_peak(ts, W-idle)`. **G2 pass** iff `median_peak(rust, W-real) ≤ 0.50 × median_peak(ts, W-real)`. **G3 pass** iff the Theil–Sen slope of RSS over the final 50% of samples is `≤ 1 MB / turn` **and** `peak(final 10%) ≤ 1.5 × peak(turns 40-60)`. **G4 pass** iff no turn exceeds **120s without state progress** and no turn exceeds a **hard deadline of 1800s**.
  - **What counts as progress for G4** (narrow, deliberately): a new message or part row, a part status transition, a tool call starting or completing, or a token-usage update. A heartbeat, a repeated identical status, or bytes still arriving on a stream that never completes a turn **do not** reset the watchdog — those are exactly the shapes a hang takes.
  - **G6 is an OS-containment requirement, not a destructor requirement.** `SIGKILL` on the parent runs no Rust `Drop`, so child reaping must come from the operating system: `prctl(PR_SET_PDEATHSIG)` plus a process group on Linux, a Job Object on Windows, and a process group with an explicit reaper on macOS. A test that passes only because the harness cleaned up is not evidence.
  - If the TS baseline cannot be measured for a given workload, that gate **fails**; it is never waived.
- Supply chain and safety: `cargo deny` for licenses/advisories; `#![forbid(unsafe_code)]` at the workspace level, asserted by a grep test over `crates/*/src/**`.
- Evidence: `.omo/evidence/task-<N>-opencode-rust.<ext>` (attemptDir = currentAttemptDir from `omo ulw-loop status --json`, `.omo/evidence/ulw/<session>/<goalId>/a<attempt>`; outside ulw-loop use `.omo/evidence/`).

## Execution strategy

### Wave 12 — Code execution, TUI, ACP

> **The `execute` tool follows jcode, not the TypeScript interpreter** (your directive). Research finding, recorded in full in `.omo/drafts/opencode-rust.md`: **jcode has no interpreter at all** — no scripting engine anywhere in its lockfile, no code-eval tool in its 26-tool roster. Two things run code: `bash` (a spawned shell) and `batch` (parallel composition of tool calls re-entering the same registry). That absence is the answer. The one thing jcode is missing — data flow between composed calls — is closed here with Rust-evaluated variable binding rather than by adopting an engine, because the real cost of the interpreter route is not the engine but the tool bridge: N async host functions re-entering the Rust registry from inside a JS event loop, which is exactly where `unsafe` and C toolchains concentrate.

**The four things you asked for**
8. No `unsafe` in first-party crates: `unsafe_code = "forbid"` at the workspace level, asserted by a grep test over `crates/*/src/**`.
9. A plugin can be written in Rust: the example plugin registers a tool and hooks and passes the conformance suite with no JavaScript involved.
10. Built-in agents follow the slimmed omo design: every agent has a negative delegation boundary, a temperature, a deny-by-default permission set, and an output envelope; **no model id string literal appears in `oc-agent`**; agents inherit the session model unless a preset or per-agent override says otherwise; `task` accepts agent type, model, reasoning effort, category shorthand, background, and `task_id` continuation.
11. The goal tool keeps a long task on track: a goal survives two compactions with its objective and counters intact, idle self-continuation fires exactly once per idle transition under all its guards, the model cannot set a system-owned status, and the Markdown projection at `.opencode/goal/<sessionID>.md` round-trips an objective edit while rejecting a status edit and saying so in the document.

**Session maintenance (the added scope)**
12. `session list --all-projects` returns the same set as the real binary's global endpoint, with project summaries.
13. `session prune` previews by default and mutates nothing without explicit confirmation; a delete removes the whole `parent_id` subtree with zero orphaned rows in any of the twelve related tables; a shared or mid-compaction session is excluded by default; the liveness guard excludes reported-active sessions and, with no server reachable, recently-touched ones.
14. Snapshot stores are removed only when unreferenced; `db vacuum` reports reclaimed bytes and refuses on insufficient disk.

**The reason this project exists**
15. **G1-G6 all pass against thresholds frozen before any Rust code existed.** The workloads, sampling rules, and the four threshold formulas are fixed in `## Verification strategy`; todo 93 measures the TypeScript baseline in **Wave 1** and commits it; Wave 14 only substitutes those measured values into the frozen formulas. A methodology-hash test fails if a formula is edited without an explicit revision bump — so the gate cannot be fitted to the result it is meant to judge. Concretely: whole-process-tree RSS at idle and on the largest real session, each ≤ 50% of the TypeScript binary's median peak on the identical workload; a ≥500-turn / ≥2-hour soak whose Theil–Sen RSS slope stays ≤ 1 MB/turn with a file watcher and two real LSP servers live; a watchdog that fails on 120s without **state progress** (heartbeats and repeated statuses do not count) and on a 1800s hard turn deadline; every bounded channel proven to coalesce or block **with progress still observable elsewhere** rather than deadlock; and zero orphaned children after clean and abnormal termination, achieved by **OS containment** (`PR_SET_PDEATHSIG` + process group on Linux, Job Object on Windows) rather than by Rust destructors, which `SIGKILL` never runs.
16. Nothing in this plan is reported as complete on the strength of a self-authored fixture: MCP is validated against a real server, LSP against two real language servers, ACP against the real client SDK, and providers against recorded real traffic.

**Honesty of the artifact**
17. Every intentional divergence from upstream is in the allow-list with a one-line reason, documented on the divergence page, and asserted by the docs test. Current entries: session-list default sort (`time_updated` instead of `time_created`); tool-output filenames carrying a session id (so a prune can attribute them); eager directory creation; the reported-version policy; **the `execute` tool's parameter contract** (upstream is `{ code: string }` running a confined interpreter — `packages/opencode/src/tool/code-mode.ts:12-20` — while this implementation takes jcode's structured sub-call shape per your directive, which changes what the model sees and must therefore be declared, not implied); **the C8 maintenance endpoints** added beyond upstream's `/api` set; and **provider coverage stated by family**, with unsupported providers named rather than silently routed through a compatible profile.
18. F1-F4 all APPROVE, and the results are surfaced to the user for an explicit okay before anything is declared done.
